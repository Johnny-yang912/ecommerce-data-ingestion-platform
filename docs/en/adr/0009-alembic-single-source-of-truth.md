# ADR-0009: Alembic is the single source of truth for schema; `create_all` removed

## Context

The project started with `Base.metadata.create_all()` at startup. It works exactly once: on an empty database.

**`create_all` only creates. It never alters.** Add a column to `models.py` and it will not appear in an existing database — `create_all` sees the table already exists and moves on, silently. The schema and the model drift apart with no error at any point, and the failure surfaces later as a runtime error on a column that "should" be there.

That makes `create_all` structurally unable to carry schema evolution, which is not an optional property for a system whose whole subject matter is data over time.

## Decision

**Alembic is the single source of truth for schema.** `Base.metadata.create_all` is removed entirely — not kept as a convenience path, because a convenience path is exactly how the two truths diverge again.

Supporting choices:

- **`env.py` pulls the connection from `settings.db_url`** and does `import models` so `Base.metadata` is populated for autogenerate.
- **`alembic.ini`'s `sqlalchemy.url` is left blank.** Filling it would create a second place where the database URL lives; `DB_URL` stays one truth (ADR-0008).
- **`Base.metadata` carries a naming convention** (`ix_`, `uq_`, `ck_`, `fk_`, `pk_`). The initial migration is generated with convention-native names.

The naming convention is the least obvious of these and the most valuable. Without it, constraint names are assigned by the database and vary between environments — so a future migration that drops or renames a constraint works on one machine and fails on another, and the failure appears long after the decision that caused it.

The workflow is: `alembic revision --autogenerate` → **review the generated script** → `alembic upgrade head`.

## Consequences

**Schema changes are reviewable artefacts.** A migration is a file in a pull request, not a side effect of a process starting.

**Drift is detectable in one command.** `check_migration_drift.py` runs `alembic upgrade head` then `compare_metadata` against `models.py`, and exits non-zero if they disagree. It is deterministic, concurrency-free and low-flake — so it *could* run in CI. It is currently manual; see [PORTFOLIO_SCOPE](../PORTFOLIO_SCOPE.md).

**Constraint names are stable and predictable across environments.**

**The cost is that "just add a column" is now two steps**, and the autogenerated script must actually be read. Autogenerate does not detect everything — column type changes and table renames in particular need human attention.

## Alternatives considered

**Keep `create_all` for local development, Alembic for deployed environments.** This is the common compromise and it is a trap: development is where schema changes are made, so it puts the change in the environment that is not tracking them. The first migration that assumes a state `create_all` never produced fails on the first deploy.

**Hand-written SQL migrations without Alembic.** No autogenerate, no version graph, no `compare_metadata` — so no way to answer "is the database what `models.py` says it is" other than by reading both.
