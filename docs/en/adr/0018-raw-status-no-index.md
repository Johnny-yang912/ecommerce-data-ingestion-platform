# ADR-0018: `raw.status` carries no index at current scale

## Context

The recovery scan selects by `status = 'pending'`. There is no index on that column, so the query cost grows with the size of the `raw` table.

ADR-0017 bounded memory and dispatch volume. It did not bound this. The obvious completion is to run `EXPLAIN`, add the index it suggests, and close the item.

**That would produce a confidently wrong answer**, and the reason is specific to this project: **all data in this system is generated by `scripts/seed_demo.py`.** Its status distribution, arrival pattern, and ratio of `pending` to terminal rows are artefacts of the generator's parameters. An index tuned against that distribution encodes the generator, not a workload.

## Decision

**No index, and the reason is recorded rather than the gap being quietly left open.**

Three specific sub-decisions cannot be made without real data:

**Partial or full?** If `pending` is a tiny fraction of the table in steady state, `WHERE status = 'pending'` as a partial index is dramatically smaller and cheaper to maintain. That ratio is a property of throughput versus worker capacity — a quantity that does not exist yet.

**Composite, and in what order?** The scan also filters on age and orders by `id`. Whether `(status, id)` or `(status, processing_started_at)` wins depends on which predicate is actually selective, which depends on the shape of real backlogs.

**Does it pay for itself?** Every index costs write throughput on the ingestion path — the hot path this entire system is built around. Trading ingestion latency for recovery-scan speed is only correct if the scan is actually the bottleneck.

## Consequences

**Query cost remains unbounded with table growth.** This is a real, recorded risk in [STATUS](../STATUS.md), not a resolved item.

**The mitigations in place are partial and honest about it**: pagination bounds what is loaded, the per-run cap bounds what is dispatched, and the grace period keeps the scan out of the ingestion path's way. None of them touch how much the database reads to answer the query.

**At current volume it does not matter.** The `raw` table is small enough that a sequential scan is fast. The decision is about not encoding a guess into the schema, not about the cost today.

## Revisit when

Real traffic exists, or the table grows large enough that the scan's query cost is measurable in the daily run. At that point the shape comes from `pg_stat_statements` — the real predicates, from the real workload — not from `EXPLAIN` over generated data.

See [PORTFOLIO_SCOPE](../PORTFOLIO_SCOPE.md) for the full reasoning and what a real system would do.

## Alternatives considered

**Add `(status)` now as a reasonable default.** Cheap, probably not wrong — and it sets a precedent for guessing at schema decisions, and would have to be dropped and replaced once the real shape is known. Index changes on a large table are not free.

**Add the index only in production.** Divergent schemas between environments, which ADR-0009 exists to prevent.
