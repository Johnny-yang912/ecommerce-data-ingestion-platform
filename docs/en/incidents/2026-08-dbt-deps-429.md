# `dbt_packages` emptied, `dbt deps` fails with "not a gzip file"

**English** | [繁體中文](../../zh-TW/incidents/2026-08-dbt-deps-429.md)

| | |
|---|---|
| **Date** | 2026-08 |
| **Impact** | Scheduled dbt tasks red; `dbt_packages/` intermittently empty |
| **Root cause** | An editor extension re-running `dbt deps` in the background, hitting a codeload rate limit |
| **Status** | Understood; mitigated by disabling the automatic behaviour |

---

## Symptom

Two symptoms that look unrelated and are not:

1. **`dbt_packages/` is empty**, so every model referencing `dbt_utils` fails to compile.
2. **`dbt deps` fails with `not a gzip file`** — a confusing error, because nothing about the command involves compression the user chose.

Because the scheduled DAG runs `dbt build`, this surfaces as **a red analytics pipeline** with an error message that points nowhere useful.

---

## Root cause

The VS Code dbt extension **runs `dbt deps` automatically in the background** — on save, on project open, and on other triggers the user does not control.

`dbt deps` downloads packages from GitHub's `codeload` endpoint. Enough automatic invocations in a short window and codeload responds **HTTP 429 (rate limited)**.

The failure then compounds in a specific way:

```
dbt deps starts
  → clears dbt_packages/ first
  → downloads from codeload
  → codeload returns 429 — an HTML/text error body, not a tarball
  → dbt writes that body to disk and tries to extract it
  → "not a gzip file"
  → dbt_packages/ is left EMPTY
```

**The destructive step happens before the fragile one.** That is why the directory ends up empty rather than stale: the old packages are already gone by the time the download fails.

---

## Why it was confusing

| What you see | Why it misleads |
|---|---|
| `not a gzip file` | Suggests a corrupt archive or a disk problem. It is actually an HTTP error body being untarred |
| Intermittent | Depends on how many times the extension fired recently — reproducible only under rate limiting |
| Nobody ran `dbt deps` | The invocation came from the editor, not the terminal, so it is absent from shell history |
| The DAG is red, but manually running dbt works | By the time you try by hand, the rate limit has expired |

The last row is the worst of them: **the manual reproduction succeeds**, which points the investigation away from the actual cause.

---

## Handling

1. **Disable the extension's automatic `dbt deps`.** The manual invocation is fine; the automatic one is what creates the burst.
2. **Re-run `dbt deps` once** to restore `dbt_packages/`, after waiting out the rate limit.
3. **Do not commit `dbt_packages/`** — it is generated, and vendoring it to dodge this would trade a transient failure for a permanent maintenance burden.

---

## Lesson

> **A tool that clears state before fetching its replacement turns any download failure into data loss.**

That pattern is worth recognising generally — it is the same shape as an `insert_overwrite` that deletes a partition before the new data is confirmed, which is precisely why `copy_partitions` uses `WRITE_TRUNCATE` on a completed copy rather than a delete-then-insert ([ADR-0044](../adr/0044-copy-partitions-sandbox-dml.md)).

The second lesson is about attribution: **a background process you did not invoke is still your dependency.** The shell history was clean, so the investigation initially assumed the network or the package registry.
