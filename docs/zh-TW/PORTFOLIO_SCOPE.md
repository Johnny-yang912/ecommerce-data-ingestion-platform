# 作品邊界：哪些刻意不做，以及為什麼

[English](../en/PORTFOLIO_SCOPE.md) | **繁體中文**

最後檢視：2026-08-24

---

## 為什麼有這份文件

這是一個作品專案。它沒有真實使用者、沒有真實上游，跑在 BigQuery sandbox 而非計費帳號上。因此有些生產系統會有的東西，這裡沒有。

把這些缺口散落在七份設計文件裡，讀起來會像是遺漏；集中在這裡，它們才是實際的樣子——**一條被量測過的邊界，而不是撞上去才發現的邊界。** 下表每一列都寫明真實系統會怎麼做，以及要讓這個系統也做到需要改變什麼。

這裡沒有任何一項是未知的工作。若是未知的，它會出現在 [STATUS](./STATUS.md) 的風險表，而不是這張表。

## 判準：作品限制，還是技術債？

不是所有沒做的事都屬於這裡。區別如下：

| | 屬於這裡（⏸ 暫緩） | 不屬於這裡 |
|---|---|---|
| **成因** | 沒有真實流量，或需要付費帳號 | 一個設計選擇，或還沒排到的工作 |
| **限制解除後** | 會照著現有設計做出來 | 可能仍然不做（⛔），或單純是 backlog（⬜） |
| **缺的是什麼** | 輸入——流量分布、閾值、觀眾 | 決策本身，或做它的時間 |

**因為沒有人知道閾值而寫不出來的規則，是作品限制；寫得出來但判斷不值得寫的規則，是決策，該進 ADR。**

**因此這張表只收 ⏸ 項目。**

> 有一列是值得點名的例外：**#8「該跑沒跑」**在 [STATUS](./STATUS.md) 裡是一項**已知風險**，不是一條 ⏸ 項目——因為它不是獨立的缺口，而是 #1 與 #3 兩者皆暫緩的*後果*。它仍然列在這裡，是因為「真實系統會怎麼做」（外部 dead-man's switch）是那兩列都沒有給出的答案。**所以兩邊的計數刻意差一。** 那些基於自身理由決定不做、而且在生產環境也會做同樣決定的東西，標在 [STATUS](./STATUS.md) 的 ⛔，理由寫在各自的 ADR 裡。目前有兩項：NUL byte 採拒絕而非淨化，以及在場景出現前不建情境專用的 `int_orders_*`。

## 三個值得展開的案例

### A. 存活告警——規則寫得出來，閾值寫不出來

這是「論述本身即交付物」最清楚的一個案例。

存活規則的閾值來自**排程宣告**，不是流量分布。`seed_demo_daily` 在台北時間 10/13/17/21 執行；一條「排程點後 90 分鐘內若無 run 就告警」的規則，今天就寫得出來，完全不需要流量。

所以不寫它的理由不是能力問題。是它周邊的整套裝置——價值閾值（延遲、錯誤率）、應對程序、升級路徑——全部需要真實流量才能長出來；而規則會住在 Grafana Cloud 的 UI 裡，既無法版控也無法審查。

實際做出來的是論述：六條存活告警的設計原則，記錄在 [design/liveness-alerting.md](./design/liveness-alerting.md)。其中一條反直覺到值得在這裡先講：

> 在 **cumulative** temporality 下，counter 序列永遠不會 absent——SDK 會持續匯出最後一個值。所以 `absent()` 偵測到的是**行程死了**，不是上游停了。要偵測「上游停了」需要的是 rate-over-window 規則，不是 absence 規則。

這個區別是量測出來才發現的，而且它不依賴真實流量。

### B. `raw.status` 索引——為什麼拿自造資料跑 `EXPLAIN` 是錯的輸入

恢復掃描以 `status='pending'` 選取列，而該欄位沒有索引。

有界掃描（分頁 + id cursor + 每輪上限）修掉的是負載下真正崩掉的那部分：記憶體與派發量。它**沒有**修掉查詢成本，那部分仍隨表成長。

直覺的做法是跑 `EXPLAIN`、照它建議建索引、收工。在這裡那是錯的，理由值得寫下來：

**這個系統裡的資料是 `seed_demo.py` 產生的。** 它的狀態分布、到達模式、`pending` 對終端狀態的比例，全部是產生器參數的產物。針對這個分布調出來的索引，編碼的是產生器，不是工作負載。

具體需要真實資料才能決定的是：

- **部分索引還是全索引？** 若穩態下 `pending` 只佔全表極小比例，`WHERE status='pending'` 的部分索引會小非常多——但那個比例是「吞吐量對 worker 容量」的性質，現在還不存在。
- **複合索引，順序如何？** 掃描同時過濾年齡、並以 `id` 排序。`(status, id)` 還是 `(status, processing_started_at)` 勝出，取決於實務上哪個述詞有選擇性。
- **它划算嗎？** 每一個索引都對攝入路徑的寫入吞吐量收費——而攝入路徑正是這個系統圍繞著建的熱路徑。

所以這個暫緩不是「還沒排到」。是**做出正確決策所需的輸入不存在，而捏造它會得到一個很有自信的錯誤答案**。

### C. BigQuery sandbox 的 60 天過期，以及它如何反向影響 Gold 層

Sandbox 對每張表強制套用 60 天分區過期。這是計費層的限制，但它改變了一個設計決策，而不只是限制了一個決策。

2026 年 8 月量測到：

1. 以 `order_date` 分區的 Gold 表，會失去 60 天以前的列——而且是靜默的。沒有錯誤、沒有警告，列數就是少了。
2. 一項相關量測推翻了雲端層文件裡先前的結論：超出 BigQuery 合法分區範圍的日期**不會**讓 build 失敗，它們會靜默落進 `__UNPARTITIONED__`。原本計畫的「合法區間 guard」因此被撤回——實際的失效模式不是原先假設的那一種。

對設計的後果是：**靜默掉列與靜默錯置，跟攝入層的 `has_clean_error` 屬於同一類危害**——不會自己出聲的問題。兩處的回應也一樣：讓它可見，而不是讓它不可能發生。`fct_orders` 帶著 `items_missing_amount` 明確暴露上捲的不完整，而不是用 `coalesce` 糊過去。

開通計費會移除這個過期限制，但不會移除它產生的設計原則。

## 模擬資料源的邊界

這個系統唯一的資料源是 `seed_demo.py`，由 `seed_demo_daily` 依排程驅動。把它的形狀講清楚很重要，因為上面好幾個暫緩項都直接源自它。

**它涵蓋什麼：**

- **走真實路徑的攝入**——每一筆都經過 `POST /orders`、佇列、CAS 認領與清洗規則。沒有任何一筆是直接插進 ODS 的。
- **兩個正交的髒資料軸**：`--dirty-rate` 產生業務規則違反；`--missing-cost-rate` 產生不完整的上游資料。兩者獨立，這正是隔離區與補值路徑得以被測試的原因。
- **足以讓分析層不流於玩具的量**：每天 800 筆訂單，分四個時段。

**因為模擬而「碰巧成立」的設計**——這不是免責聲明，每一列都有具體後果：

| 碰巧成立的設計 | 真實流量會對它做什麼 |
|---|---|
| 所有灌資料時段都落在同一個 UTC 日分區 | 全天候攝入躲不掉 UTC 換日點；台北 00:00–08:00 會落進前一天 |
| Hard Gate 用「最新 UTC 日分區」代理「最新批次」 | 在連續攝入下它會退化成「今天到目前為止」，**把稀釋問題在單一天之內重演一次** |
| Freshness 不需要阻斷權（沒資料 = 沒人灌 = 無害） | 上游中斷是一次事故——**但 freshness 不是偵測它的東西。** 它量的是 `ods.received_at` = extract 那一跳，對上游在結構上是盲的。真實系統要加的是 Raw 側的量測，而不是把 freshness 接成一道閘門 |
| 26h／50h 的 freshness 門檻 | **不變。** 它們來自**載入**節奏（每天一次 extract → 24h + 2h 寬限），不是攝入節奏。在 24/7 攝入下倉庫仍然是每晚載入一次。會改變它們的是 extract 改成每小時或串流 |

**它不涵蓋什麼：**

- **一天之內的品質變動。** 髒資料率每天從五個值裡確定性地選一個，因此日內恆定。這是暫緩項 #2 的直接成因。
- **上游的 schema 漂移。** 新欄位或改名從不出現。additive staging 與 `on_schema_change` 的機制是靠手動演練，不是靠產生器。
- **對抗性或畸形流量**，超出已修掉的特定案例（NUL byte、items 裡的 NaN/Inf）之外的都沒有。
- **第二個時區跨越日界的流量**——暫緩項 #13 的直接成因。
- **突發與背壓。** 負載特性由 `load_test.py` 按需提供，不來自排程的產生器。
