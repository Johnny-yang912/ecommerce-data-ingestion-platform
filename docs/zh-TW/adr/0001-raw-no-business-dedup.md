# ADR-0001：Raw 層不做業務去重

[English](../../en/adr/0001-raw-no-business-dedup.md) | **繁體中文**

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-05 |
| **層** | 攝入 — Raw |

---

## 背景

`POST /orders` 把 request body 逐字寫進 Raw 表。顯而易見的防守動作是在 `raw.order_id` 上加 `UNIQUE`：在門口就拒絕重複提交，管線後面就再也不用想去重這件事。

有三件事反對這麼做。

**重複提交不必然是冗餘的。** 同一個 `order_id` 提交兩次，可能帶著不同的欄位——一個上游若在補齊資料後重送，第二次帶的資訊嚴格多於第一次。拒絕第二次，等於丟掉第一次沒有的資料。

**提交頻率本身就是訊號。** 同一個 `order_id` 在一分鐘內來了四十次是有意義的：客戶端的重試迴圈、設定錯誤的上游，或是攻擊。`UNIQUE` 約束把這個訊號轉換成一個約束違反，然後丟掉它。

**這個系統自己會製造重複。** `_enqueue()` 刻意吞掉 broker 故障、仍然回傳 `200 pending`，因為 Raw 那一列已經 commit 落地了（見 ADR-0013）。但在 HTTP 層逾時的客戶端會重送。**在 Raw 拒絕那些請求，等於對這個系統自己的維運者隱藏這個系統自己降級行為的後果。**

## 決策

`raw.order_id` **有索引，但沒有 unique**。每一個被接受的 `POST /orders` 都恰好產生一列 Raw，不管先前看過什麼。

去重的責任下放給下游的 ODS（ADR-0005）。

## 後果

**Raw 的列數按設計高於 ODS**，而兩者的差是一個監控量，不是錯誤。它回答「這條管線正在吸收多少冗餘提交？」——這個問題在重複被拒絕的情況下根本問不出來。

**Raw 保持為真正的 landing 層。** 它記錄「到達了什麼」，不對到達的東西做判斷——**正是這一點，讓下游的每一個判斷日後都能在不重新攝入的前提下被修訂。**

**代價是儲存空間**，以及一個必須真的執行唯一性的下游層。如果 ODS 的約束是錯的，上游沒有任何東西會抓到。

## 考慮過的替代方案

**在 `raw.order_id` 上加 `UNIQUE`。** 丟失互補欄位、丟失頻率訊號，而且回給客戶端一個 `409`——那是客戶端無法與真實失敗區分的東西，所以一個行為良好的客戶端還是會重試。

**在 endpoint 內先讀後寫。** 同樣的語意問題，再加上在攝入熱路徑上對一張只會成長的表每次都做一次 `SELECT`。
