# ADR-0002：`has_clean_error` 非阻斷

[English](../../en/adr/0002-has-clean-error-non-blocking.md) | **繁體中文**

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-05 |
| **層** | 資料品質 — ODS |

---

## 背景

ODS 層對每一筆訂單做兩件事：格式正規化（強制轉換——去空白、大小寫、型別對齊），以及業務規則驗證（`age` 是否在合理區間、`customer_name` 是否超過軟性長度上限，諸如此類）。

格式正規化的答案很明顯：轉換完就往下走。業務規則驗證則不然。當一條規則失敗時，這一層必須在「拒絕這筆記錄」與「連同失敗一起記下來」之間做選擇。

有三股力量把答案推離「拒絕」：

**ODS 是不可變錨點。** 它是唯一一個「每一筆被接受的訂單都恰好存在一次、且已攤平可查詢」的地方。若髒資料被拒絕，錨點就不完整——而且沒有分母。當那些失敗從未被寫入時，「3% 的訂單驗證失敗」這句話根本無法回答。

**Raw 不能替代。** Raw 表確實保有原始 payload，但那是未解析的 JSON。不重做一次整個攤平流程，它無法被對帳、聚合或 join。

**品質規則會變。** `DQ_RULE_VERSION` 目前是 v4；`age` 上限從 120 調到 130，`customer_name` 軟性上限從 100 調到 150。一筆在 v2 規則下被拒絕的記錄，在 v4 規則下可能完全乾淨。若當初的回應是拒絕，那筆記錄除非從來源重新攝入否則無法救回——而來源在上游，可能早就沒有它了。

## 決策

`clean_order()` 回傳 `(ods, has_clean_error, clean_error_message)`。業務規則違反會把 `has_clean_error` 設為 `True` 並記下 error codes。**ODS 的寫入無條件繼續。**

`has_schema_drift` 是一個平行且獨立的訊號，具有相同的非阻斷性質。兩者從不混用：一個講的是**值違反了業務規則**，另一個講的是**上游契約的形狀改變了**。

阻斷發生在下游、逐筆、在 `int_` 層的 Row Filter——不在這裡。

## 後果

**ODS 保持完整。** 每一筆被接受的訂單，不論品質如何都恰好存在一次，所以每個品質指標都有真實的分母，層與層之間的對帳是算術而不是猜測。

**規則變更變得可以回溯套用。** 因為那些列還在，它們可以在不重新攝入任何東西的前提下，用新版規則重新評估。**單是這一個性質，就是整套 Proposal B 再評估機制與 `quality_events` 狀態機得以存在的原因**——如果當初拒絕了髒資料，這些東西一個都不會存在。

**代價是：任何下游消費者都不得為了業務報表直接讀 ODS 或 `stg_`。** 那些層按設計就含有髒資料。這條規則靠層契約與測試維護，不靠 schema——沒有任何東西能在物理上擋住一個粗心的查詢。

**第二個代價是：列數永遠需要一個品質限定詞。** 「昨天有幾筆訂單」有兩個都正確的答案，任何沒講清楚是哪一個的報表都是錯的。

## 邊界：這個決策**不**涵蓋什麼

非阻斷適用於**業務規則違反**，不適用於**儲存層面的不可能**。

欄位溢位（`DataError`）或字串內含 NUL byte（`ValueError`）根本寫不進去。這些會快速失敗到終端 `error` 狀態，永遠不會到達 ODS。把它們當成「標記後繼續」不是一個選項——沒有東西可以繼續下去。

那條邊界本身是另一個決策，見 ADR-0006。

## 考慮過的替代方案

**在 ODS 拒絕。** 失去錨點性質，並讓規則演進變得無法救回。兩點都不成立，否決。

**在 Raw 層阻斷。** Raw 的職責是記錄「到達了什麼」，包含重複與垃圾——見 ADR-0001 與 ADR-0003。把品質判斷搬到那裡，等於把兩個刻意不同職責的層壓成一層。

**把髒資料寫到另一張 ODS 表。** 每個下游查詢都得 `UNION`，而且「恰好一次」的不變式會被拆散在兩張表裡——這代表它可能以任何單表約束都抓不到的方式被違反。
