# ADR-0007：服務間驗證用 static API Key，不用 JWT

[English](../../en/adr/0007-static-api-key-not-jwt.md) | **繁體中文**

| | |

| **日期** | 2026-06 |

## 背景

這個服務是內部資料網格中的一個攝取單元。它的呼叫者是一小群穩定的上游服務——machine-to-machine。**沒有人類使用者**，所以沒有登入、沒有 session，也沒有需要攜帶的使用者身分。

JWT 是「加上驗證」的反射性答案，而它買到的東西在這裡大多不相干：由獨立身分提供者簽發之聲明的無狀態驗證、短生命期 token，以及一個使用者主體。這裡沒有身分提供者，沒有可對應到使用者 session 的過期概念，也沒有「這是哪個上游服務」以外的主體。

## 決策

一個 static 的 `X-API-Key` header，對照從 `.env` 載入的映射解析：

```
API_KEYS = key1:client_a,key2:client_a,key3:client_b
```

- **多把 key 可以對應同一個 `client_id`**，輪替就是這樣運作的：讓新舊 key 重疊、重新部署、再撤掉舊的。
- 比對使用 `secrets.compare_digest`——constant-time，所以無法用逐字元的 timing 洩漏猜出 key。
- 缺失或無效的 key 回 **401**（header 依賴設 `auto_error=False`，因為 FastAPI 預設回 403，而 403 的意思是「已驗證但無權限」——那是另一回事）。
- 映射中格式錯誤的項目**略過而非致命**，讓單一壞項無法拖垮整份設定。
- 被拒絕的 key **只記前六個字元**。

解析出的 `client_id` 身兼二職：

1. 它落到 Raw 與 ODS 成為 `source_client_id`——**資料血緣的起點**，回答「這一列是哪個上游送的」。
2. 它被設在 `request.state` 上並成為限流的鍵，所以限額適用於「已驗證的身分」而非「網路位置」。

第二點有一個值得記錄的時機限制：**依賴解析階段是唯一夠早的時刻。** slowapi 的限流檢查跑在它 wrapper 的最前面，比 endpoint 本體還早——如果改在 endpoint 本體內設定 `client_id`，`key_func` 就來不及讀到它。

## 後果

**新增一個來源是有計畫的基建事件**，不是執行期操作：改 `.env`、重新部署。對一組固定的內部上游而言，這本來就是變更實際發生的方式。

**撤銷一把 key 需要一次部署。** 這是真正的代價。在目前的規模下這個暴露窗口可以接受；面對外部或自助式客戶就不行。

**血緣隨驗證免費附帶。** 因為 `source_client_id` 是從已驗證的 key 導出的，而不是從 payload 讀來的，所以上游無法靠在 body 裡填別的值來假冒他人。

**`source_client_id` 為 `NULL` 是有意義的，不是缺值。** 它標記「這一列不是經由已驗證 API 進來的」——手動重放、backfill、直接寫 DB。Raw 刻意把「來源未知」保留為一個可表達的狀態，而不是發明一個佔位值。

## 考慮過的替代方案

**JWT。** 買到的是「對一個這裡並不存在的身分提供者所簽發之聲明」的無狀態驗證與過期機制，換來的是 key 管理、時鐘偏移處理，以及一套比「讓兩把 static key 重疊」更複雜的輪替流程。

**以 DB 為後端的 `api_clients` 表。** 能提供執行期的 key 管理與即時撤銷。目前否決，因為它在攝入熱路徑上加了一次資料庫讀取，還加了一個要維護的管理介面——而呼叫者集合的變動頻率趨近於零。

## 何時重新檢視

當服務擴張為多 domain 或多租戶，或取得了非內部的呼叫者——屆時執行期 key 管理不再是選項，`api_clients` 表就是正確的形狀。
