# ADR-0013：broker 等待必須有界

## 背景

`POST /orders` 寫入 Raw、commit，然後派工。如果派工用的是函式庫預設值，等待會退回到 OS 層的 DNS 與 TCP 逾時。

實測：`docker compose stop redis` 之後，單次 `POST /orders` **阻塞 19 秒**才回應。

那之所以不可接受，是這個系統設計上的性質，不是一般性的效能顧慮。**broker 對攝入路徑而言是可選的。** 如果派工失敗，Raw 那一列已經以 `pending` commit 落地，恢復掃描會撿起它。**在所有真正重要的意義上，這個請求已經成功了。**

> **一個可選的下游，絕不該有能力讓必要路徑為它的失敗付出代價。**

## 決策

派工路徑上的每一個等待都有明確上界：

| 設定 | 值 | 目的 |
|---|---|---|
| `socket_connect_timeout` | 2s | 建立連線的上限 |
| `socket_timeout` | 2s | 操作本身的上限 |
| `retry_on_timeout` | `False` | 逾時就是答案，不是再等一次的理由 |
| `broker_connection_timeout` | 2s | Celery 層級的上限 |
| `task_publish_retry_policy.max_retries` | 1 | 給瞬斷一次重試，然後放棄 |

`_enqueue()` **吞掉所有例外**並回傳一個布林值。它從不把失敗往上傳，因為 Raw 那一列已經 commit 了——回 `500` 會讓客戶端重送，為一筆其實已被接受的訂單灌出一批 `duplicate`（ADR-0001、ADR-0003）。

因此回應語意是：**`200`，狀態 `pending`**——「已受理；處理會延遲」。

`task_publish_retry_policy` 上限設為一次嘗試，理由很具體：**重試越久，越只是把「已經有兜底的失敗」轉換成請求延遲。** 兜底存在；重點是快點抵達它。

## 後果

**broker 中斷降級的是吞吐量，不是正確性。** 記錄以 `pending` 落地，broker 回來後恢復掃描把它們排空。

**這與 `has_clean_error` 非阻斷是同一條原則**，只是用在不同的層：*已經成立的事實，不因為下游故障而回退*。Raw 那一列存在；客戶端被如實告知。

**2 秒仍然不是零**，而且在併發下會嚴重複合——那正是 ADR-0014 存在的目的。這個決策限制單次呼叫的成本；斷路器在持續故障下把它完全移除。

**⚠️ `_enqueue()` 是同步函式，可能阻塞整個逾時時間。** async 路徑上的每一個呼叫者都必須用 `asyncio.to_thread` 包起來，否則一次 broker 中斷會卡住整個 event loop。

## 考慮過的替代方案

**保留預設值，讓客戶端自己逾時。** 客戶端無法區分「你的訂單被拒絕了」與「你的訂單被接受了但回應很慢」，所以它會重送——為已經存下的資料製造重複。

**派工失敗時回 `503`。** 對佇列誠實，對請求不誠實：訂單**確實**被接受了。`503` 招來的正是那個製造重複雜訊的重送。

**在 commit Raw 之前派工。** 會讓派工失敗重新變得有意義——代價是為可能不存在的列派出任務。
