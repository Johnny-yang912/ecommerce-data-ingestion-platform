# ADR-0017：恢復掃描本身也必須有界

## 背景

斷路器（ADR-0014）達成了它的任務：broker 中斷期間攝入維持全速。**這代表 `pending` 也以全速累積。**

掃描原本的實作是「選出所有 `pending`，逐一派工」。在一次會產生數十萬列的中斷下，那等於把整批載入一個 Python list 再迭代。**它並沒有消除崩潰——它把崩潰從攝入路徑搬到了恢復路徑上**，而那更糟，因為恢復路徑本來是要事後收拾的那一個。

那個直覺修法裡還有一個不明顯的陷阱。**光加 `LIMIT` 沒有用：派工不會改變 `status`。** 下一頁對同一份資料跑同一個查詢，會再次撈回同樣的前幾列，永遠如此。

## 決策

五道界限，各自關掉一種不同的失效：

| 界限 | 值 | 關掉什麼 |
|---|---|---|
| 每頁大小 | `SCAN_BATCH_SIZE = 5000` | 無界的記憶體 |
| 游標 | `WHERE id > :last_id ORDER BY id` | `LIMIT` 單獨使用的重撈迴圈 |
| 每輪頁數 | `SCAN_MAX_ROUNDS = 20` | 單一 task 獨佔一個 worker 槽位 |
| Redis 鎖 | key + 300s TTL | 兩輪掃描重疊 |
| 寬限期 | `PENDING_GRACE_SECONDS = 60` | 與攝入快路徑競爭 |

每輪上限是 `20 × 5000 = 100,000`。剩下的等下一個 tick——**掃描本來就是週期性的，「一次跑完」從來不是需求。**

**鎖用 Lua 的 compare-and-delete 釋放**，不是 `GET` 之後 `DEL`。那兩步不是原子的：在中間鎖可能已經過期並被別人取得，此時 delete 會刪掉**別人的**鎖——讓兩輪掃描同時進行，正是這把鎖存在要防止的事。

鎖的 TTL 取一個掃描間隔：task 若崩潰而沒能釋放，最多犧牲一輪 tick。

## 後果

**對 120,000 筆積壓的實測：**

| 掃描 | 派發 |
|---|---|
| #1 | 100,000（每輪上限） |
| #2 | 20,000 |

ODS 恰好成長 120,000，零重複。

**掃描現在是刻意不精確的，而那是安全的。** 它可能重派一筆已經在佇列裡的記錄。CAS（ADR-0004）讓輸家立即返回，所以代價是一個浪費掉的 worker 槽位與一次 DB 來回，絕不會是重複寫入。目標是限制住記憶體與派發量；精確從來不是目標。

**⚠️ 還有一道界限缺著：查詢成本。** `raw.status` 沒有索引，所以分頁限制住載入與派發的量，但沒有限制資料庫為了找到它們而掃描的量。見 ADR-0018。

## 一項相關紀律：門檻住在哪裡

`STALE_PROCESSING_MINUTES` 與 `PENDING_GRACE_SECONDS` 住在自己的模組 `recovery_policy.py`，而不是它們原本所在的 `process.py`。

理由是一次真實事故。`check_raw_pending.py` 是一支**唯讀探針**，它從這兩個常數推導告警線而非寫死。它從 `process.py` import 它們——**因而繼承了整條寫入路徑的依賴樹**。OTel 上線時 `process.py` 多了一行 `from telemetry import ...`，於是探針在**檢查任何東西之前**就死在 `ModuleNotFoundError: No module named 'opentelemetry'`，因為 Airflow 的 `venvs/analytics` 映像還沒重建。

> **單一個共用常數，把一支探針綁到了它根本不執行的程式碼路徑上。**

把常數抽進一個零第三方依賴的模組，從根上修好了它；`tests/test_script_deps.py` 釘住它，讓它不必靠人記得。

它們**刻意不放進 `config.py`**：那個模組的邊界是「只放環境值」，而這兩個是程式行為（ADR-0008）。`scan_interval_seconds` 反過來確實是環境設定，所以它留在那裡——因此門檻推導同時讀兩邊是正確的。

## 考慮過的替代方案

**`LIMIT` 不加游標。** 上面描述的重撈迴圈。

**派工時把列標記為 `queued`。** 能讓「已入列」在資料庫裡可見，讓掃描跳過它們——**設計更乾淨，規模也更大**：它為狀態機增加一個狀態，並帶來一種新的失效模式（推送失敗後卡在 `queued` 的列，需要它們自己的清掃）。已記錄為「若哪天要重新檢視佇列」的方向。

**一次跑完全部。** 無限期獨佔一個 worker 槽位，並讓鎖的 TTL 無法估算。
