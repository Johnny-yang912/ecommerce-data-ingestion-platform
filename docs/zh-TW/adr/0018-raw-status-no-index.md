# ADR-0018：現階段 `raw.status` 不建索引

## 背景

恢復掃描以 `status = 'pending'` 選取。那個欄位上沒有索引，所以查詢成本隨 `raw` 表的大小成長。

ADR-0017 限制住了記憶體與派發量，但沒有限制這個。顯而易見的收尾是跑一次 `EXPLAIN`、照它建議加索引、把這一項關掉。

**那會得到一個很有自信的錯誤答案**，而理由是這個專案特有的：**這個系統裡的所有資料都是 `scripts/seed_demo.py` 產生的。** 它的狀態分布、到達模式、`pending` 對終端狀態的比例，全都是產生器參數的產物。**針對那個分布調出來的索引，編碼的是產生器，不是工作負載。**

## 決策

**不建索引，而且把理由記下來，而不是把缺口靜靜留著。**

有三個子決策在沒有真實資料時無法做出：

**部分索引還是全索引？** 若穩態下 `pending` 只佔全表極小比例，`WHERE status = 'pending'` 的部分索引會小很多、維護也便宜很多。那個比例是「吞吐量對 worker 容量」的性質——一個目前還不存在的量。

**複合索引，順序如何？** 掃描同時過濾年齡、並以 `id` 排序。`(status, id)` 還是 `(status, processing_started_at)` 勝出，取決於哪個述詞實際上有選擇性，而那取決於真實積壓的形狀。

**它划算嗎？** 每一個索引都對攝入路徑的寫入吞吐量收費——而攝入路徑正是這整個系統圍繞著建的熱路徑。拿攝入延遲去換恢復掃描的速度，只有在掃描確實是瓶頸時才是對的。

## 後果

**查詢成本仍然隨表成長而無界。** 這在 [STATUS](../STATUS.md) 裡是一項真實且被記錄的風險，不是一個已解決的項目。

**目前的緩解是局部的，而且對此誠實**：分頁限制住載入量、每輪上限限制住派發量、寬限期讓掃描不擋攝入路徑的路。**這三者都沒有碰到「資料庫為了回答這個查詢要讀多少」。**

**在目前的量下這無關緊要。** `raw` 表小到循序掃描很快。這個決策是關於「不要把一個猜測編碼進 schema」，而不是關於今天的成本。

## 何時重新檢視

存在真實流量，或表大到掃描的查詢成本在每日跑批中可被量測。屆時形狀來自 `pg_stat_statements`——真實工作負載的真實述詞——而不是來自對產生資料跑的 `EXPLAIN`。

完整推理與真實系統的做法見 [PORTFOLIO_SCOPE](../PORTFOLIO_SCOPE.md)。

## 考慮過的替代方案

**現在就加 `(status)` 當作合理預設。** 便宜、大概也不算錯——而它為「猜測 schema 決策」立下先例，而且一旦知道真正的形狀就得刪掉重建。**大表上的索引變更並不免費。**

**只在生產環境加索引。** 各環境 schema 分歧，而那正是 ADR-0009 存在要防止的。
