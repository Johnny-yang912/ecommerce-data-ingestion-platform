# ADR-0019：批次載入，不做串流

## 背景

攝入路徑是即時的：一筆訂單在毫秒內就進到 ODS。把這個性質往下游延伸、讓資料一落地就串流進 BigQuery，是很誘人的想法。

有兩件事反對它，而其中只有一件是關於成本。

**下游消費者是 BI。** 儀表板與報表以 T+1 或每小時的節奏更新。倉庫裡的次分鐘級新鮮度會是一個沒有人讀的性質。

**批次才讓「窗口式品質檢查」成為可能。** Hard Gate 斷言的是最新分區的錯誤率（ADR-0028）。「對**什麼**取比率」只有在存在一個批次時才回答得出來。串流沒有批次邊界，所以那道 run 層級的閘門——阻止壞掉的上游抵達 Gold 的那個東西——**沒有東西可以被界定範圍**。

成本是第三個理由，也是最不有趣的：BigQuery 的批次 load job 免費，streaming insert 不免費。

## 決策

**只用批次 load job。** `client.load_table_from_json(...)` 搭配 `WRITE_APPEND`。抽取路徑上任何地方都不用 streaming insert。

巢狀的 `items` 以原生 JSON 物件落地，而非序列化字串，讓形狀能存活到 `stg_`。

## 後果

**窗口式品質控管能運作**，因為存在一個窗口：Hard Gate 的口徑、freshness 斷言、`rpt_quality_events_daily` 的日粒度，全都建立在批次邊界上。

**失敗可重跑。** 一個批次要嘛載入了、要嘛沒有；失敗時 watermark 不推進，下一輪用 `>=` 重新選取（ADR-0023）。**部分串流出去的資料集沒有這樣一個乾淨的重試點。**

**攝入層與分析層保持解耦。** 分析層的失敗無法對攝入層形成背壓，因為攝入路徑上沒有任何東西在等它。

**代價是延遲**：一筆訂單要到下一次排程抽取之後才在倉庫裡可見，而不是立即可見。**那正是刻意做的交換。**

## 考慮過的替代方案

**Streaming insert。** 會提供沒有人消費的次分鐘級新鮮度、按列計費，而且——決定性的一點——移除品質閘門所依賴的批次邊界。

**Micro-batch（分鐘級）。** 保有批次邊界的中間路線。刻意不採用：新鮮度需求不存在，而且分區預算與報表口徑都以日為前提。若哪天真的要改，`get_watermark()` 就是那個接縫（ADR-0023）。

## 何時重新檢視

出現需要次日級新鮮度的下游消費者——一個即時模型，或一個真的有觀眾的營運儀表板。
