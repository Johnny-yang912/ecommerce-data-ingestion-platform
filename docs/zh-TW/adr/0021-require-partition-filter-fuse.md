# ADR-0021：`require_partition_filter` 作為成本保險絲

[English](../../en/adr/0021-require-partition-filter-fuse.md) | **繁體中文**

| **日期** | 2026-06 |

## 背景

BigQuery 按掃描位元組數計費。**分區表並不保護你免於全表掃描**——它只是讓**有過濾**的查詢變便宜。`SELECT * FROM staging.orders` 不帶 `WHERE` 會掃過每一個分區，並全額計費。

真實會發生的失效不是惡意或無知，而是一句臨時查詢忘了寫 `WHERE`，或某個 dbt model 在重構時弄丟了過濾條件。這兩者都不會大聲失敗——查詢回傳正確結果，成本在之後的帳單上才出現。

## 決策

`orders` staging 表設 `require_partition_filter = True`。

不帶分區過濾的查詢現在會**立即失敗**並給出明確錯誤，而不是昂貴地成功。

這個設定在 `TableSpec` 裡逐表宣告，不是全域套用——因為它並非普遍正確（ADR-0022）。

## 後果

**失效模式從「昂貴且靜默」變成「免費且大聲」。** 查詢時的錯誤能在幾秒內修正；一張帳單不行。

**下游模型必須刻意帶分區過濾。** `stg_orders` 用回看窗讀取，這自然滿足保險絲——**它為了正確性所需要的過濾，正好就是保險絲要求的過濾。**

**`stg_orders` 自己不設保險絲。** 它是 dbt 管理的表，消費者是 `int_` 模型與 Hard Gate 測試，而 Hard Gate 在作為儀表時必須能對全表斷言（ADR-0028）。在那裡套用保險絲會擋掉設計本身要求的查詢。

**代價是探索性查詢的摩擦。** 有人翻 staging 時每次都得寫過濾條件。**那正是刻意的摩擦**——那個習慣本來就是保險絲要建立的東西。

## 考慮過的替代方案

**改用專案層級的成本配額。** 配額是在出血開始之後止血，而且是帳號範圍的，所以一句粗心的查詢可以耗掉其他所有東西的預算。**保險絲是阻止那句查詢，而不是為損害設上限。**

**靠 review 與慣例。** 有效，直到失效的那一次；而回饋迴路是一張帳單，不是一則錯誤訊息。

**對每張表一致套用。** 否決——見 ADR-0022，那裡主要消費者的存取模式本質上就是全掃描，保險絲會擋掉正確的行為。
