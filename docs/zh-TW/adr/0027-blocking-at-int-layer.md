# ADR-0027：阻斷發生在 `int_`，不在 ODS

[English](../../en/adr/0027-blocking-at-int-layer.md) | **繁體中文**

|---|---|
| **狀態** | Accepted |
| **日期** | 2026-06 |

## 背景

髒資料必須在抵達儀表板之前的某處被擋下。問題是**在哪裡**，而從攝入層往下的每一層都是候選。

「早點擋」是直覺的答案——快速失敗、把壞資料擋在外面。ADR-0002 已經否決了在 ODS 擋，理由關於錨點與規則演進。但**否決一個地點不等於選定另一個**，而這個選擇對中間的每一層都有後果。

## 決策

**品質控管的責任隨下游逐步收緊。阻斷恰好發生在一個地方：`int_` 層。**

| 層 | 品質要求 | 髒資料 |
|---|---|---|
| Raw | 無 | 逐字保留 |
| ODS（Bronze／錨點） | 標記，絕不拒絕 | 保留 |
| `stg_`（Silver 入口） | 與 ODS 相同 | 保留 |
| **`int_`（Gold 入口）** | **只有有效乾淨的記錄通過** | **→ `int_orders_quarantine`** |
| `dim_`／`fct_`（Gold） | 最乾淨的一層 | 不存在 |
| `rpt_` | 與 Gold 相同 | 不存在 |

有兩個機制運作在不同粒度上，不可混淆：

- **Hard Gate**（run 層級，掛在 `stg_`）：source 是不是**整個**壞了？擋下整個 run（ADR-0028）。
- **Row Filter**（逐筆層級，在 `int_` 內）：**這一筆**能用嗎？把它導向隔離區（ADR-0029）。

## 為何是 `int_` 而不是 `stg_`

`stg_` 是來源的 1:1 鏡像：改名、轉型、去重，僅此而已。在那裡過濾會讓它不再是鏡像，而「拿 `stg_` 對 ODS」也就不再是有意義的對帳。

`int_` 是第一個已經在做語意工作的層——join、衍生欄位、業務邏輯。**一筆記錄「可不可用」是一個語意判斷，所以它歸屬於第一個有資格做語意判斷的層。**

## 後果

**`int_` 以上的每一層都有完整的母體**，所以品質指標有分母、對帳是算術。

**隔離區是一個去處，不是一次刪除。** `int_orders_quarantine` 保存被擋下的記錄與它們的 error codes，**這才讓 Proposal B 的回流成為可能**（ADR-0030）。一個把列丟掉的過濾器會讓再評估變得不可能。

**這個劃分由不變式測試把關。** `int_orders` 與 `int_orders_quarantine` 必須對 `stg_orders` 互斥且窮盡。有一個 singular test 斷言它——沒有它的話，任一模型 `WHERE` 子句的錯誤都會靜默地遺失或重複列。這不是理論風險：BigQuery 的三值邏輯讓一列很容易同時不滿足**兩邊**的條件而從兩張表同時消失（ADR-0029）。

**代價是這份契約不由 schema 強制。** 沒有任何東西在物理上阻止一份報表直接讀 `stg_` 並納入髒資料。它由層契約、測試，以及 ADR-0049 所持有。

## 考慮過的替代方案

**在 ODS 擋。** ADR-0002——失去錨點，並讓規則演進無法救回。

**在 `stg_` 擋。** 破壞 1:1 鏡像性質，以及倚賴它的那個對帳。

**在 `dim_`／`fct_` 擋。** 代表每一個 Gold 模型都要重複那個過濾，而每一個都是一個可能寫錯的地方。**在 Gold 入口過濾一次，代表下游一切都可以假設輸入是乾淨的。**

**在 BI 工具裡過濾。** 把一份資料品質契約放在一個沒有版控、沒有測試、沒有審查的地方。
