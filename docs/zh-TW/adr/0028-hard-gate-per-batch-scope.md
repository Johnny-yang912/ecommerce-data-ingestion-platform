# ADR-0028：Hard Gate 的口徑是逐批；全表是儀表，不是閘門

[English](../../en/adr/0028-hard-gate-per-batch-scope.md) | **繁體中文**

| | |
|---|---|
| **狀態** | Accepted——曾就地修訂，見變更紀錄 |
| **日期** | 2026-08 |
| **層** | 資料品質 — dbt `stg_` |

---

## 背景

Hard Gate 是 run 層級的阻斷機制：掛在 `stg_orders` 上的測試，失敗會中止整個 dbt run，讓 `int_`／`dim_`／`fct_` 保留上一次的乾淨狀態。

**它守的東西很容易被說錯。它不是清潔度檢查。** 髒資料由 `int_` 的 Row Filter 逐筆處理（ADR-0029），落進 `int_orders_quarantine`。Hard Gate 存在是為了回答另一個問題：**source 是不是整個壞了？** 它是突變偵測器，不是品質量表。

這道閘門原本的口徑是全表：`stg_orders` 全部資料的錯誤率。那個口徑浮現了三個問題，而只有第一個是顯而易見的。

**它會隨資料集成長而失去靈敏度——這是實測，不是推論。** 全表的分母是累積歷史，所以單一批災難性資料會被稀釋。實測連續四批錯誤率都在 10% 以上（2026-08-05 那批甚至是 **100%** 髒），而同期全表數字是 **9.122%**。**閘門一次都沒有觸發過。** 一道用來防範突發失效的機制，光是因為系統跑得久了，就會在履行職責上越來越差——它以「變老」的方式失效，而且無聲無息。

**它無法自癒。** 上游修好之後新資料是乾淨的——但歷史髒資料永遠留在分母裡。全表比率不會回落到閾值以下。**問題解決之後閘門還是紅的**，唯一的解除方式是調高閾值或關掉測試。**兩者都在訓練維運者忽略這道閘門**，那比沒有閘門更糟。

**它的分母會被日曆推動。** Sandbox 在 60 天時讓分區過期。推算顯示 2026-09-05 前後，一批 300 筆、0% 髒的資料會到期蒸發——全表比率會因此從約 9% 跳到 **12%**。管線會在**沒有任何人改動任何東西、也沒有任何新髒資料進來**的情況下自己紅掉並被永久擋住。

> **會被日曆觸發的指標，不該擁有阻斷權。**

保留期政策、一次補跑 backfill、一次 `--full-refresh`，都以同樣的方式推動這個分母，理由也相同：**它對品質以外的事情敏感。**

## 決策

兩條斷言，不同口徑、不同權限：

| | 口徑 | 閾值 | 嚴重度 | 角色 |
|---|---|---|---|---|
| `hard_gate_latest_batch_error_rate` | 最新 `received_at` 分區 | 15% | `error` | **閘門**——擋下整個 run |
| `monitor_dataset_error_rate` | 全表 | 10% | `warn` | **儀表**——只提供能見度 |

閘門的分母固定為一批的規模，因此靈敏度不會隨歷史漂移。儀表保留資料集整體健康度的能見度，並**刻意不給它阻斷權**。

兩者都由自訂 generic test `macros/error_rate_below.sql` 實作，它接受一個 `scope` 參數。

## 後果

**靈敏度在資料集的整個生命週期內保持穩定。** 一批 20% 壞掉的資料，在第 1 天和第 1000 天同樣會觸發閘門。

**閘門會自己清除。** 上游修好之後下一批就是乾淨的，閘門自動打開，不需要人介入，也不需要動閾值。

**慢性滲漏不會觸發它。** 任何單批都不超過 15% 的髒資料會通過閘門。**這是接受，不是疏漏**：那些記錄由 Row Filter 逐筆隔離，趨勢由 `rpt_quality_events_daily` 追蹤。閘門不是處理那種失效模式的機制。

**現在有兩個閾值需要維持其意義，而其中一個貼得不太舒服。** 15% 與 10% 是佔位值——沒有真實上游的分布可以拿來導出它們（見 [PORTFOLIO_SCOPE](../PORTFOLIO_SCOPE.md)）。具體地說：模擬上游的 `--dirty-rate` 是 0.12，而在 n≈200 時批次錯誤率的標準差約 2.3 個百分點。**大約每十批就會有一批純因隨機波動而觸發閘門**——實測有一批落在 14.5%，只差 0.5 個百分點。要把誤觸率壓到約 1%，門檻需要接近 18%。

> **閘門紅燈時，先排除這種誤觸**，不要預設把它讀成上游異常。

**`latest_partition` 不等於「這一次 extract」。** Staging 沒有 load batch id，所以日分區只是代理。當一次 extract 因 watermark 用 `>=` 而跨兩天時，只有較新那天會被斷言。要精確到批次，就得在 extract 時寫入批次欄位——而那會讓 `stg_orders` 的 `raw_id` 去重決勝變成非決定性的。那是一個獨立的決策，而且還沒有做。另外，分區邊界是 **UTC**，在台北時間 08:00 換日。

## 考慮過的替代方案

**`dbt_utils.expression_is_true`。** 技術上不可行，而且值得記下為什麼：它是逐列測試，會把條件摺進 `WHERE NOT(...)`，而錯誤率需要 `countif()/count(*)`——那是聚合。BigQuery 直接拒絕，錯誤訊息是 `Aggregate function COUNTIF not allowed in WHERE clause`。比率斷言必須在聚合層級表達，這正是自訂 generic 用 `HAVING`（不加 `GROUP BY` ＝ 對選定範圍取單一值）的原因；回傳一列就代表閾值被突破。

**讓全表那條斷言也保有阻斷權。** 否決：不可自癒，理由如上。**能阻斷的那條斷言，決定了整個機制的品質上限。**

**在 `stg_` 逐筆阻斷。** 否決：那會違反「`stg_` 保留一切、含髒資料」的層契約（ADR-0002、ADR-0027）。逐筆阻斷在下一層有它指定的歸屬。

## 何時重新檢視

當存在真實上游、且其錯誤率分布可被觀測時。屆時閾值應該由那個分布導出，而不是被選定。

## 變更紀錄

**2026-08——口徑從全表改為逐批。** 原本的閘門以阻斷嚴重度斷言整個 `stg_orders` 的錯誤率。因背景中的三個理由而被取代；全表斷言保留下來但降級為 `warn`。機制本身（`stg_orders` 上的 run 層級聚合斷言）沒有改變，所以這是一次修訂，而非一條新的 ADR。
