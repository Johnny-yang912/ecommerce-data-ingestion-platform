# ADR-0030：Proposal B——事件驅動的再評估，不重跑管線

[English](../../en/adr/0030-proposal-b-event-driven-reevaluation.md) | **繁體中文**

## 背景

品質規則會變。`age` 上限從 120 調到 130；`customer_name` 軟性上限從 100 調到 150。每一次放寬，都代表某些在舊規則下被隔離的記錄，在新規則下是合法的。

直覺的修法是重跑管線：重讀 Raw、重新清洗、重新寫入。**在這裡辦不到，而且也不該這麼做。**

**辦不到**，因為 ODS 是不可變的（ADR-0002）——沒有東西可以重寫。**不該**，因為重跑會摧毀稽核軌跡：那筆記錄將不再顯示它曾經被隔離過，也不再顯示是在哪個規則版本下。

## 決策

**再評估產生事件，不產生變更。** `reevaluate_quality.py` 讀取候選、對它們重跑當前規則，並在——且僅在——判定確實改變時，append 到 `quality_events`。

其中有四個決策：

**候選來自 BigQuery 的 `int_` 層。** 使用與 Row Filter 完全相同的有效品質狀態定義（ADR-0029），所以產生者與消費者不可能對「誰被隔離了」有不同意見。

**狀態的判定對 PostgreSQL 做，不對 BigQuery 做。** **冪等性不可以建立在一個會過期的鏡像上**——sandbox 的 60 天分區過期意味著 BigQuery 會遺失 PostgreSQL 仍然持有的歷史。從鏡像讀候選沒問題；判斷「事件是否已經存在」則不行。

**只在狀態確實改變時 append 事件。** 「重新評估過、仍然隔離」什麼都不寫。這讓事件表**成為它自己的冪等閘門**：跑兩次與跑一次結果相同，不需要另一個去重鍵。

**dry-run 是預設值。** commit 是一個明確的旗標，而那個 DAG 的 `schedule=None`（ADR-0037）代表它只在有人手動觸發時才跑。

## 可重現性：兩道守衛

幾個月後重跑一條規則，必須為同一筆記錄、基於同一個理由得到同一個判定。有兩個機制強制這件事：

**`business_clean` 新增了 `as_of` 參數。** 與時間相關的規則（從日期推導的年齡、一個已經關閉的窗口）否則會純粹因為時鐘往前走而得到不同答案。`as_of` 把評估釘在那筆記錄自己的時間上。

**`NON_REPRODUCIBLE_CODES` 擋掉「證據消失了」的 promotion。** 有些 error code 事後無法重新檢查——當初造成錯誤的那個東西已經不在了、無從查驗。沒有這道守衛，**證據的缺席會被讀成乾淨的證據**，那筆記錄會**基於錯誤的理由**被 promote。這些 code 被完全排除在 promotion 之外。

> **一次看不見記錄為何失敗的再評估，不可以下結論說它沒有失敗。**

## 後果

**規則演進成為一個有 runbook 的例行操作**，端到端演練過四次：v3（promote 15 筆）、v4（3 筆），以及一次 fixture 重建期間背靠背的 v2→v3（16 筆）與 v3→v4（15 筆）。四次全部冪等、ODS 從未被修改、對照組留在隔離區。

**ODS 與倉庫之間的分歧變得可解釋而非神祕。** `dq_rule_version` 記錄攝入當下的真相；`quality_events` 記錄演進之後的真相。「為什麼 ODS 說髒而 Gold 說乾淨？」有一個可查詢的答案。

**收緊方向是對稱的但尚未被演練。** `re_quarantination` 存在於狀態機中，而還沒有任何場景產生過它，所以 `rpt_quality_events_daily.re_quarantines` 目前仍是 0。

**`permanently_rejected` 只能來自人。** 自動任務永不寫入它、也永不覆蓋它——在 PostgreSQL 的寫入目標上強制，而非僅靠 BigQuery 側的過濾。

## 考慮過的替代方案

**從 Raw 重跑管線。** 摧毀稽核軌跡，並牴觸不可變錨點。

**更新 ODS 的 `has_clean_error`。** 違反 bounded writeback（ADR-0032）；同樣遺失歷史。

**自動排程它。** 否決——規則變更是一個有審查步驟的人為決定，而它的影響半徑應該在 commit 之前先用 dry-run 檢視（ADR-0037）。
