# ADR-0032：Bounded writeback——倉庫的判斷不回流進 ODS

[English](../../en/adr/0032-bounded-writeback.md) | **繁體中文**

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-07 |
| **層** | 資料品質 — 一致性 |

---

## 背景

再評估發生在下游：候選在倉庫裡被辨識出來，判定在那裡、或由一個讀取那裡的工作算出來。**結果必須寫到某個地方。**

誘人的目的地是 ODS 本身——把被 promote 的記錄設成 `has_clean_error = FALSE`，然後下游一切都自動正確，不需要任何特殊處理。`int_` 不需要合成邏輯、不需要 `LEFT JOIN`、不會有 `COALESCE` 陷阱。

**它同時也會溶解掉整個架構所倚賴的那個性質。**

## 決策

**回流只寫 `quality_events`。ODS 永不被修改。**

```
❌ 禁止：倉庫 → UPDATE ODS 的欄位
✅ 允許：倉庫 → INSERT 進 quality_events
```

`quality_events` 是一份專為接收這件事而設計的稽核日誌。ODS 是不可變錨點。

## 後果

**錨點保持可信。** 「這個系統在攝入當下、在哪一套規則下、相信了什麼？」永遠有答案。一旦 ODS 可從下游寫入，這個問題對**任何**一列都再也回答不了——**包括那些從來沒有被回寫過的列，因為摧毀這個保證的是「可能性」本身。**

**ODS 與倉庫之間的分歧成為預期之內且可解釋的**，而不是一個症狀。它恰好有兩個來源，各自的處理方式不同：

| 來源 | 如何被解釋 |
|---|---|
| 規則版本演進 | `dq_rule_version` + `quality_events`——可查詢、帶時戳 |
| 情境專用模型接受了與該情境無關的錯誤 | 讀那個模型的 SQL 與它的 dbt description——靜態，沒有執行期追蹤表 |

第二個是一條刻意的邊界：情境修復需要的是**可解釋**，不是**執行期被稽核**。SQL 裡的文件已經足夠，而一張追蹤表會是沒有人查詢的機械結構。

**代價：每個消費者都必須自己合成有效狀態。** ADR-0029 的 `LEFT JOIN` 與 `COALESCE` 陷阱就是從這裡來的——**真實的複雜度，刻意付出，換取那個錨點。**

**有一類問題被永久放在觸及範圍之外**，而這是誠實的限制。`force=true` 重放與規則再評估**都**修不了**值產生的缺陷**——一個清洗 bug 汙染了已經 `processed` 的記錄裡的值（sentinel 清單把 `"na"` = North America 當成 null，把某個欄位在數千列上洗成 NULL）。

再評估幫不上忙：**它的輸入就是那些被汙染的值。** 就算它看得出來，bounded writeback 也禁止它寫值。那條路徑需要完全不同的機制——一個從 Raw payload 出發的批次修正——它被設計為 Proposal C 並刻意未實作。

> **若不明講這條邊界，「Raw 逐字保留使重建成為可能」這個承諾就沒有東西背書。Proposal C 就是背書它的那個東西。**

## 考慮過的替代方案

**promote 時更新 ODS 的 `has_clean_error`。** 簡化每一個消費者，並摧毀錨點、稽核軌跡，以及「回答系統在攝入當下相信了什麼」的能力。

**在 ODS 旁另建一張可變的「當前狀態」表。** 保持 ODS 不可變，卻在隔壁一張表重新引入同一個問題：兩個地方持有品質判定，而它們可以不一致。`quality_events` 避開它的方式是 append-only——**它持有的是「轉移」，不是「狀態」。**

**讓倉庫成為品質真相的唯一來源。** 依 ADR-0030 的理由否決：sandbox 的 60 天分區過期意味著倉庫會遺失 PostgreSQL 仍然持有的歷史。**冪等性不可以建立在一個會過期的鏡像上。**
