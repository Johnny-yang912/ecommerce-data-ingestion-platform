# ADR-0033：歷史品質指標永不回溯改寫

[English](../../en/adr/0033-historical-metrics-never-rewritten.md) | **繁體中文**

| | |
|---|---|

| **日期** | 2026-07 |
| **層** | 資料品質 — 指標 |

## 背景

假設有 100 筆記錄在規則版本 v1 下被隔離，而 v2 後來 promote 了其中 15 筆。

**v1 的隔離率是多少？**

有兩個站得住腳的答案，而選錯會讓所有歷史品質數字失去意義：

- **「仍然是當時那個數字。」** v1 隔離了 100 筆。那是**發生過的事**。
- **「向下修正為 85。」** 其中 15 筆其實不髒，所以歷史比率被高估了。

第二個很誘人，因為它感覺更精確。**它是錯的答案，因為它混淆了「系統當時判定了什麼」與「我們現在相信什麼」。**

## 決策

**歷史指標永不改寫。** `quality_events` 是 append-only 的，所以基於它計算的指標自動穩定——**那些數字不會變，因為沒有東西可以被改變。**

Promotion 被計為**它自己的獨立指標**，在它自己的時間軸上：

```sql
-- v1 下的初始隔離率——這個數字永遠不變
SELECT countif(to_state = 'quarantined') / count(*)
FROM quality_events
WHERE event_type = 'initial_evaluation' AND rule_version = 'v1'

-- v2 promote 了幾筆——獨立指標，不覆蓋上面那個
SELECT count(*)
FROM quality_events
WHERE event_type = 'promotion' AND rule_version = 'v2'
```

## 後果

**一個品質指標的意思是「系統在當時、依當時的規則所判定的結果」。** 那是關於系統運作的一個事實，而它保持為真。

**規則變更的影響成為一個獨立可見的量**，而不是被靜默吸收進一個被修正過的歷史數字裡。「v2 promote 了 15 筆」比「v1 的比率其實是 85%」更有用，**因為它指出了原因。**

**兩條時間軸並存**，這正是品質報告拆成兩張表的原因（ADR-0049）：`rpt_quality_events_daily` 在**事件**軸上（那天發生了什麼，寫下後不可變），`rpt_quality_backlog` 是**快照**（現在有什麼在隔離區，每次 run 都變）。

**沒有人能悄悄改善過去。** 一份顯示品質正在下滑的報表，無法靠放寬一條規則、讓歷史重新算過來修好。放寬會以 promotion 的形式出現，出現在它發生的那一天。

**代價是「現在有幾筆是髒的」與「三月被判定為髒的有幾筆」需要不同的查詢。** 兩個問題、兩個答案，刻意不統一——同樣的拆分在另一條邊界上見 ADR-0034。

## 考慮過的替代方案

**用當前規則重算歷史比率。** 每個歷史數字都變成今天規則的函數，所以每當一條規則移動，一張圖的形狀就會回溯改變。**一條會自己改寫的趨勢線，無法支撐任何結論。**

**兩個都存——原始的與修正的。** 讓每個指標倍增，並在每個使用點強迫一次選擇。實務上其中一個會變成大家引用的那個，另一個變成雜訊。

**每日快照當前狀態並據此報告。** 失去區分「曾被判定為髒」與「當前是髒的」的能力，**而那正是讓規則演進可稽核的那個區分。**
