# ADR-0034：Tier-1 營運指標與 Tier-2 分析指標的邊界

[English](../../en/adr/0034-tier-1-tier-2-metrics.md) | **繁體中文**

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-07 |
| **層** | 資料品質 — 指標 |

---

## 背景

「資料品質狀況如何？」是兩個問題穿著同一件句子的外衣。

**「現在有東西壞掉嗎？」** 需要幾分鐘內給出答案、低基數，而且需要在**倉庫掛掉時仍然讀得到**——因為倉庫掛掉正是可能壞掉的東西之一。

**「品質按品類、按客戶、按規則版本的趨勢如何？」** 需要高基數與任意切片，而且沒有人需要在幾分鐘內得到它。

**為兩者建一套機制，會產生一個兩邊都做不好的東西**：不是一個被基數淹沒的指標後端，就是一個假裝自己是告警的倉庫查詢。

## 決策

兩層，邊界明確。

| | Tier 1 — 營運 | Tier 2 — 分析 |
|---|---|---|
| 延遲 | 分鐘級 | 日／週批次 |
| 基數 | 刻意低 | 任意 |
| 在哪 | OTel 指標 + structlog 的 `quality_metric` 事件 | 倉庫裡的 `rpt_quality_*` |
| 問題 | **現在**有東西壞掉嗎？ | 品質的**趨勢**如何？ |
| 倉庫中斷時仍可用 | 是 | 否 |

**判準：高基數切片按定義屬於倉庫。** 指標後端按時間序列計費；倉庫按查詢計費。同時按客戶、品類、規則版本切片，在其中一邊很便宜，在另一邊是災難。

## 後果

**Tier 1 保持負擔得起。** 序列預算實測為 320 個活躍序列——免費額度的 3.2%。**那個數字之所以達得到，正是因為這條邊界被執行了。**

**那份預算裡反直覺的部分值得記錄**：貴的指標結果是**自動的**那些，不是自訂的那些。三個 Drop view 移除了 `http.server.request/response.size` 與 `flower.task.runtime.seconds`，它們合計佔了 **27%**——而後者用毫秒級的 bucket 量測一個秒級的值，也就是**解析度為零的資料**。

> **你沒有寫的埋點，仍然是你要付錢的埋點。**

**Tier 1 的答案在倉庫不可用時仍然存活**，而那很重要，因為「分析管線壞了」正是有人在問的那個時刻。

**業務／DQ 指標目前在 tier 1 暫緩**，理由是這個專案特有的：模擬上游每天從五個值裡確定性地挑一個髒資料率，所以它**在一天之內是恆定的**。分鐘級的錯誤率說不出 `rpt_quality_events_daily` 沒說過的事。見 [PORTFOLIO_SCOPE](../PORTFOLIO_SCOPE.md)。

**代價是同一個概念被表達了兩次**，在兩個系統裡、用兩份定義。它們必須靠紀律保持一致；沒有任何東西自動檢查它。

## 考慮過的替代方案

**只有一層：全部放倉庫。** 便宜又簡單，而它在事故期間什麼都回答不了——**中斷與診斷共用一個故障域。**

**只有一層：全部放指標後端。** 要嘛捨棄高基數維度（失去分析），要嘛付錢買它們（負擔不起——序列數隨每個維度倍增）。

**從 tier-2 的表推導 tier-1 指標。** 繼承倉庫的延遲與它的故障域，**而那恰好移除了 tier 1 存在的唯二理由。**
