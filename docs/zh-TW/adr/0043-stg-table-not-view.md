# ADR-0043：`stg_` 建表，不建 view

## 背景

dbt 的主流慣例把 staging model 物化成 **view**：輕量鏡像、儲存便宜、永遠反映最新來源。**這個專案刻意偏離它。**

物化其實是兩個決策——先「物化 vs 虛擬」，再「怎麼物化」。這份記錄講前者；後者見 ADR-0044。

## 決策

`stg_orders` 是一張實體表。四股力量，而第一個是決定性的：

**① 它切斷保險絲的傳播。** staging 帶著 `require_partition_filter = True` 作為成本保險絲（ADR-0021）。**view 只是被儲存起來的 SQL**——不帶 `received_at` 過濾去查它，會往下傳播到那道保險絲並回 400。所以 view 會強迫**每一個**下游消費者、包含 Hard Gate 測試，都記得帶分區過濾。**實體表把保險絲擋在 `stg_` 這一層。**

**② 去重只付一次。** 那個 window function 去重是 `stg_` 的核心工作。view 會讓每個下游都重算它——N 個消費者，每次 run 就 N 次。表算一次然後共用。

**③ DAG 根部的一致快照。** `stg_` 是轉換 DAG 的根，被許多下游讀取。把它物化成表，讓所有下游站在同一個「執行時凍結」的快照上，不受併發寫入 append-only staging 的影響。

> 這是**一致性**，不是**持久性**。資料錨點仍然是 ODS——`stg_` 隨時可以從 staging 重建。

**④ 它是增量的前提。** 「成本不隨歷史成長」倚賴分區層級的 `insert_overwrite`，而那**要求**一張實體的分區表。**view 沒有實體分區可以替換，所以它在結構上做不到。**

## 後果

**下游模型不受保險絲牽制**，這才讓 Hard Gate 在作為儀表時能對全表斷言（ADR-0028）。

**代價是儲存與物化延遲**——`stg_` 只在一次 run 之後才反映來源。兩者都可接受：BigQuery 的儲存非常便宜，而每一個下游消費者本來就跑在 dbt 的批次節奏上，沒有人需要 view 的「永遠最新」。

**這次偏離慣例是由在地的技術力量正當化的，不是由原則。** 這裡沒有一條「鏡像就該是實心的」通則——如果保險絲是關的、而且只有一個下游消費者，view 會是更好的選擇。

## 考慮過的替代方案

**View（慣例做法）。** 儲存最便宜、永遠最新，代價是保險絲傳播到每個消費者、去重重複、沒有 run 級快照、也沒有通往增量的路。**那四項裡有三項是這個專案特有的。**

**Ephemeral。** 被 inline 進每個下游，所以它有 view 的所有問題，外加無法被臨時查詢檢視。
