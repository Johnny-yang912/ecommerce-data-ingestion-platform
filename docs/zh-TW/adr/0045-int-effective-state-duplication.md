# ADR-0045：`int_` 層刻意重複實作有效狀態邏輯，而非抽共用模型

## 背景

`int_orders` 與 `int_orders_quarantine` 需要同一段邏輯：合成有效品質狀態（ADR-0029）。直覺是把它抽成共用模型——**重複正是我們被訓練要消除的東西**。

檯面上有三個選項，而關於它們有一個常見的信念是錯的：

| | 做法 | 實體物件 | JOIN 執行次數 | 互補性由什麼保證 |
|---|---|---|---|---|
| A | 共用 **ephemeral** 模型輸出 `is_effectively_clean` | 不增加 | **每個下游各一次** | 機制（一個布林 + 它的否定） |
| B | 共用小表 `int_quality_current` + 一個 macro | +1 張表 | 總共一次 | 機制（macro） |
| **C（採用）** | 每個模型 inline 同一段 CTE | 不增加 | 每個下游各一次 | **紀律 + 一個測試** |

**值得澄清的誤解：** A 與 C 編譯出來的 SQL 幾乎相同。ephemeral 模型會**被 inline 進每一個下游**，所以它既不會建立額外關聯，**也不會省下任何 JOIN 執行**。只有 B 真的減少 JOIN 次數。

> **A vs C 純粹是維護面的取捨，不是成本面的。**

## 決策

採用 C——那段區塊被寫兩次，在兩個檔案裡都用 `═══` 註解圍起來，而且**必須保持逐位元組相同**。

三個理由：

1. **今天只有兩個消費者**，所以重複的代價低於多一層 `ref` 間接的認知代價。
2. **每個模型檔自給自足**——讀 `int_orders.sql` 就看得到整個決策邏輯，與 DQ 文件的範例逐字相符，不必在三個檔案之間追來追去。
3. **代價（互補性從機制保證降為紀律保證）可以用一個測試買回來。**

最後那一點就是這個模式：**花一個測試，把紀律保證換回機制保證。** 同樣的手法出現在 Gold 層（ADR-0047）。

## 對齊清單

任一模型變更時都要走一遍。每一列都是一種破壞劃分不變式的方式：

| # | 檢查 | 弄錯的後果 |
|---|---|---|
| 1 | 兩邊 `is_effectively_clean` 定義**完全相同**；一邊 `WHERE cond`、另一邊 `WHERE NOT cond` | 條件不互補 → 有些列兩張表都不在（**靜默遺失**）或都在（下游重複計數） |
| 2 | `coalesce(..., false)` **不可拿掉** | `has_clean_error=TRUE` 且無事件時，`FALSE OR NULL = NULL`；`WHERE NOT NULL` 也是 NULL → **該列同時從兩張表消失** |
| 3 | 一律 `LEFT JOIN` | 不小心用了 INNER，會丟掉每一列沒有品質事件的記錄 |
| 4 | window 的 `partition by` / `order by` 決勝鍵一致 | 兩邊為同一列挑到不同事件 → 劃分破裂 |
| 5 | `effective_quality_state` 的 CASE 分支一致 | 血緣標籤不一致，`rpt_quality_*` 算錯 |
| 6 | 兩個模型使用**相同的物化方式** | 一個增量、一個全量 → 劃分在 run 之間破裂 |
| 7 | `assert_orders_split_is_partition` 維持 `severity: error`，**永不降級、永不 `--exclude`** | 在選項 C 之下，它是唯一的自動化安全網 |

> **#2 最容易被忽略。** `is_effectively_clean` 的三種狀態——TRUE／FALSE／**NULL**——之中，NULL 會讓一列從**兩張**表同時消失，而且是靜默的。**劃分測試就是為了這件事而存在。**

## 後果

**每個模型都能單獨讀懂**，而這很重要，因為這是系統最核心的品質決策被表達出來的那一層。

**安全網是單一個測試，而它是承重的。** 第 7 項不是風格偏好——**降級那個測試，等於移除選擇 C 的全部正當性。**

**代價是真實的，而且在任一模型的每一次變更時都要付。** 它被對齊清單所限制，而不是被善意所限制。

## 何時重新檢視

**當第三份副本出現時**——例如啟用情境專用的 `int_orders_*` 模型。到了三個消費者，重複的代價就開始高於間接的代價，那段區塊應該收斂成選項 A 或 B。
