# ADR-0047：度量上捲到表頭，由不變式測試把關

## 背景

有了雙事實表——`fct_orders`（表頭粒度）與 `fct_order_items`（明細粒度）——最大的風險不是把它們建錯，而是**同一個數字存在兩個地方，而且可能不一致**。

| | A：上捲進 `fct_orders` | B：金額只放明細事實表 | **C（採用）** |
|---|---|---|---|
| 「這個月的訂單數與營收」 | 單表查詢 | 必須 join + group by | 單表查詢 |
| 兩個數字不一致 | 可能，沒有東西守著 | 不可能（單一真相） | **不可能（有測試守著）** |
| 額外成本 | 0 | 0 | 一個 singular test |

## 決策

把金額上捲進 `fct_orders`，並用 `assert_fct_orders_rollup_matches_items` 斷言逐訂單相等。

這與 ADR-0045 是**同一個手法**：花一個測試，把紀律保證升級成機制保證，並換回單表可查詢性。

**那個測試裡必須用 `is distinct from` 而非 `=`。** 金額嚴格傳播 NULL，而 `NULL = NULL` 得到的是 NULL 而非 TRUE——所以 `=` 會讓「兩邊都是 NULL」的列被 `WHERE` 靜默濾掉，**而那正是最可能出錯的情況**。

## 這個測試抓到了它並非為此而設計的東西

第一批真正多品項的訂單落地那天（2026-08），它在 **39 列**上變紅。`item_count` 與 `total_quantity` 完全相符；只有金額不同——**差 1 ULP**。

成因：`FLOAT64` 上的 `SUM()` 不具結合律，而上捲與測試的重新聚合走了不同的執行計畫。

它之所以潛伏那麼久，是因為在那之前，60 天窗口內的每一筆訂單都**恰好只有一個品項**——單值的 `SUM()` 沒有累加，因此沒有順序效應。

**修法是把金額改成 `NUMERIC`，而不是把測試放寬成容差比較。** 容差會藏起真正的缺陷：浮點數金額。

## `SUM` 會靜默吞掉你刻意保留的 NULL

`int_order_items` 嚴格傳播 NULL——衍生金額上不做 `coalesce`。上捲處有一個陷阱：**BigQuery 的 `SUM()` 會忽略 NULL。** 若某一個品項的 `discount_pct` 在 `safe_cast` 失敗，該訂單的 `net_amount` 就少了恰好一個品項的量，**沒有錯誤、沒有痕跡**。

補救刻意**不是** `COALESCE`——那是有損的、單向的，而且違反「補值屬於 DAG 邊緣」這條規則。取而代之的是讓不完整**明確化**：

```
fct_orders.items_missing_amount   ← 這筆訂單有幾個品項的金額算不出來
```

由消費者決定這個總和可不可信。**我們不代替他們決定 NULL 等於零；我們給他們決定的依據。**

相關且同一原則：`item_count = 0` 把「一筆沒有品項的訂單」表達成一個**值**而非一個**缺席**，而 `fct_orders` 必須 `LEFT JOIN` 那個上捲——**用 `INNER` 會讓那整類訂單從 Gold 消失。**

## 後果

**最常見的那個問題有了單表可查詢性**，而且沒有通常伴隨它的風險。

**一個浮點數金額的 bug 是被一致性測試抓到的，而不是被使用者抓到的。** 那在時機上是運氣、在設計上不是——**但它是「去斷言那些『顯然成立』的不變式」的論據。**

**代價是一個 singular test 與一份必須保持同步的上捲**——而那是被機制強制的，那正是重點。

## 考慮過的替代方案

**金額只放明細事實表。** 不一致在建構上就不可能，而最常見的業務問題每次都需要 join 與 group by。

**上捲但不加測試。** 兩個數字可以漂移，而沒有東西說哪個是對的。**那個浮點數缺陷會靜默地上線。**

**把測試放寬成容差比較。** 會把一個真實的 bug 藏在一個 epsilon 後面。
