# ADR-0048：只建兩個維度、採 SCD1；事實表帶當時的快照

[English](../../en/adr/0048-two-dimensions-scd1.md) | **繁體中文**

|---|---|
| **狀態** | Accepted |
| **日期** | 2026-08 |
| **層** | 轉換 — dbt `dim_`／`fct_` |

## 背景

教科書式的星型結構會誘使你建一整組維度：日期、地理、顧客、產品，再加一個裝低基數旗標的 junk dimension。**在這裡它們大多是投機性的。**

而第二個問題緊接著來：顧客屬性會隨時間改變，那這個模型需要 SCD2 嗎？

## 決策

**只建 `dim_customer` 與 `dim_product`。** 其餘全部退化到事實表上：

| 不建 | 為何 |
|---|---|
| `dim_date` | 目前沒有會計年度或假日的需求；`order_date` 可以直接 `date_trunc` |
| `dim_geography` | 不存在一份一致的地理主檔——抽出它只是把欄位搬個位置再 join 回來，而且寬表在 BigQuery 的欄式儲存裡成本很低 |
| Junk dimension | 省下列儲存不是 BigQuery 會有的問題 |

**SCD1，帶明確的決勝鍵。** 兩個維度都沒有獨立主檔——屬性隨著每一筆訂單抵達——所以沒有一份獨立的變更來源可追蹤。決勝鍵是必要的：**沒有它的話，同一天多筆訂單中哪一筆勝出會隨執行順序漂移**，讓維度變成非決定性的。

## SCD1 的失真由事實表買回來

SCD1 會把歷史訂單蓋上**當前**的屬性——一位三月是銀卡的顧客，今天讀起來是白金卡。修法不需要 SCD2：

```
fct_orders.membership_tier_at_order   ← 下單當下的等級
```

**訂單上攜帶的顧客屬性，本來就是一份時點快照。** 讓事實表帶著它們，**以零基礎設施得到 type-2 的效果**：

| 問題 | 讀哪裡 |
|---|---|
| **目前**是白金卡的顧客的總消費 | `dim_customer.membership_tier` |
| 在**還是**白金卡時所下的訂單 | `fct_orders.membership_tier_at_order` |

## SCD2 已設計、刻意未啟用

Trigger 是**開通計費**，而理由不是嫌麻煩——是在 sandbox 上 SCD2 **會壞**。

dbt snapshot 是一張**有狀態的**表。一旦 60 天的表過期把它吃掉，**它就永久消失了**。**那與 `fct_` 的全量重建在類別上完全不同**，後者下一次 run 就會從來源自癒。

> **一張處於強制過期之下的有狀態表，不是緩慢變化維度。它是一個會失憶的維度。**

## 後果

**模型很小，而且每一張表都掙得了它的位置。** 沒有任何維度是為了滿足一張架構圖而存在。

**兩個時間性問題今天都答得出來**，而且不需要 snapshot 基礎設施。

**寬的事實表**，那在欄式儲存裡是正確的取捨——沒被讀到的欄位在查詢時不花錢。

**`dim_product` 的屬性衝突是標記而非阻斷**：同一個 `product_id` 可能在不同訂單上帶著不同的名稱或品類抵達。2026-08 實測，**342 個 `product_id` 中有 163 個**衝突——根因是 `load_test.py` 把 `product_id` 與它的屬性從兩次獨立的隨機抽樣取得，之後已修正。**標記而非阻斷，意味著那個產生器的 bug 在資料裡是可見的**，而不是被藏在一次失敗的 build 後面。

## 考慮過的替代方案

**完整的 Kimball 維度組。** 更符合教科書，而 `dim_date` 與 `dim_geography` 會為了沒有人提出過的需求而存在——**為投機性的好處付永久的維護成本**。與 ADR-0027 對情境模型的立場是同一條原則。

**一開始就做 SCD2。** 會用基礎設施去回答一個已經有欄位可以回答的時間性問題——而且在 sandbox 上會壞。

**SCD1 但不設決勝鍵。** 維度內容在 run 之間非決定性，**而且是以沒有任何測試會明顯抓到的方式。**
