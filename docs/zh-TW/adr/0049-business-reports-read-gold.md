# ADR-0049：業務報表永遠讀 Gold；品質報告拆成兩張表

## 背景

把 `rpt_` 直接接在 `int_` 上當成一句罐頭查詢，很方便，**而它是一個反模式**。四個理由，其中兩個是通用的、兩個是這個專案架構特有的。

| # | 理由 | 繞過 `fct_` 的後果 |
|---|---|---|
| 1 | 每個指標一份定義 | 「營收」有兩條血緣 → 兩個數字，而沒有人知道哪個錯 |
| 2 | 不要重做 Gold 已經做過的語意決策 | unknown member、`item_count=0` 的 LEFT JOIN——全都得再抄一次 |
| 3 | 它讓既有測試失效 | `assert_fct_orders_rollup_matches_items` 守的是 `fct_orders` 的上捲；若 `rpt_` 從 `int_` 重算，**那個測試完全涵蓋不到它** |
| 4 | ⭐ 它推翻了一個架構前提 | 「`int_` 只在 DAG 內部被消費」是 `int_` 不分區的**唯一**理由。`rpt_` 去讀它，等於把它從內部建材升級為**公開契約** → 分區決策需要重新檢視，而 `int_` 變得無法重構 |

## 決策

**業務報表只讀 `dim_`／`fct_`。**

**合法的例外是品質報告。** 被隔離的列按定義永遠不會抵達 Gold，所以 `rpt_quality_*` 必須從 `int_orders_quarantine` 與 `stg_quality_events` 取材。

> ⚠️ 那個例外帶著一個容易犯的錯：**品質比率的分母是整個 `stg_orders`，含髒資料——不是 `fct_orders`。** 用 Gold 當分母，`quarantine_rate` 會恆等於零，**因為把那些列拿掉正是 Row Filter 做的事。**

## 品質報告拆成兩張表

原本草擬的單一 `rpt_quality_daily` 把兩個性質相反的東西混在一起：

| | `rpt_quality_events_daily` | `rpt_quality_backlog` |
|---|---|---|
| 軸 | **事件軸**（`event_at`） | **快照**（隔離區當前內容） |
| 一列代表 | 「那天發生了 N 次品質事件」 | 「現在有 N 筆訂單卡著」 |
| 會被回溯改寫嗎？ | **不會**（append-only） | 會——它**就是**當前狀態 |
| 可以增量嗎？ | ✅ 軸與變化來源對齊 | ❌ 本質上不行 |

**為何 backlog 不能直接從事件軸累加。** 理論上 `backlog(t) = 累計 quarantined − promoted − rejected`，因為事件流是狀態的完整導數。但 `quality_events` 有 60 天分區過期——**一旦過期，那個累加的起點就不見了，而且失真是單向的**：起點只會少算 quarantined，所以 backlog 會被系統性低估。快照表直接讀 `int_orders_quarantine`，免疫於事件保留窗。

**為何事件表不掛在攝入軸上。** 按 `received_at` 分組，代表今天 promote 一筆三個月前的訂單，會**改寫三個月前那一列的組成**——那是狀態、不是事件，而且它會讓「v1 攔截了多少」隨時間漂移，直接牴觸 ADR-0033。

## 後果

**每個指標有一條血緣**，而 Gold 的語意決策只做一次。

**既有測試真的涵蓋得到報表**，因為報表讀的正是那些測試所守的表。

**`int_` 保持可重構**——它仍然是內部建材，**那正是讓它「不分區」的決策繼續成立的原因。**

## 關於誠實的一段話

教科書給 `rpt_` 的正當理由是「預先聚合以換取效能與成本」，**而以這個專案的資料量而言，那個理由一文不值**。文件刻意不宣稱它，因為那會是假的。

真正的理由是：**每個指標一份固定定義**，以及 **BI 不必自己組 join**。放任報表作者在 BI 工具裡自由聚合 `fct_`，指標定義就會漂移進 BI 工具——**在這個規模下，那才是 `rpt_` 實際上防止的東西。**
