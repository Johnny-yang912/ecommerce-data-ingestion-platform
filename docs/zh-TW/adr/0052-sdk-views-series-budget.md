# ADR-0052：用 SDK Views 控制序列預算——貴的是自動指標

[English](../../en/adr/0052-sdk-views-series-budget.md) | **繁體中文**

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-08-17 |
| **層** | 可觀測性 |

---

## 背景

指標後端按**活躍時間序列**計費，而每一組獨特的「指標名稱 + 屬性值」組合都會產生一條序列。**基數是乘法的**：三個屬性、各十個值，一個指標就是一千條序列。

免費額度是 10,000。直覺會認為風險在自訂埋點——那些你刻意加的指標、刻意選的屬性。

**那個直覺是錯的，而是量測顯示了這件事。**

## 決策

**用 SDK Views 控制序列預算**，而且**驗證結果而非假設它**。

實測：**320 條活躍序列——免費額度的 3.2%。**

自訂埋點刻意維持低基數：

| 指標 | 回答什麼 |
|---|---|
| `orders.raw.result` | 終端狀態分布 |
| `orders.processing.duration` | 處理延遲 |
| `orders.retry` | 重試壓力 |
| `circuit_breaker.state` | 斷路器是否開路 |
| `recovery_scan.dispatched` | 掃描有沒有在運作 |

另外兩個由自動埋點免費提供、且確實值得保留：`http.server.duration`（P50/95/99）與 `db.client.connections.usage`（連線池壓力）。

### 那個反直覺的發現

**三個 Drop view 移除的是沒有人寫的指標**，而它們佔了**總量的 27%**：

| 被移除 | 為何 |
|---|---|
| `http.server.request.size` | 沒有人會對這個系統問這個問題 |
| `http.server.response.size` | 同上 |
| `flower.task.runtime.seconds` | **用毫秒級的 bucket 量測一個秒級的值**——解析度為零的資料 |

> **你沒有寫的埋點，仍然是你要付錢的埋點。**

`flower` 那個 histogram 是最鮮明的例子：它不只是沒必要，它是**沒有意義的**。每一次觀測都落進同一個 bucket，所以它消耗序列去記錄「什麼都沒有」。**沒有人選擇它——它隨著一個函式庫抵達，而只有一次量測找到了它。**

## 後果

**預算是被驗證過的，不是被假設的。** 「免費額度的 3.2%」是一個在埋點變更後可以重新檢查的數字，而不是一個期望。

**新增一個自訂指標既便宜又可預測**，因為低基數的紀律已經建立，而餘裕是真實的。

**任何依賴升級之後都必須重做一次這個稽核。** 一個函式庫可以在次要版本裡新增一個 histogram，**而沒有任何東西會通知你**。這是這個決策的常駐成本。

**View 是做這件事的正確層級。** 在 Collector 端丟棄，仍然要在行程內付 SDK 的聚合成本；在 SDK 端丟棄，代表那條序列從未被建立。

## 考慮過的替代方案

**什麼都不丟，倚賴免費額度夠大方。** 27% 被三個回答不了任何問題的指標吃掉，**而且下一個依賴新增第四個時完全不會有訊號。**

**改在 Collector 端過濾。** 可行，而且照樣付了行程內的聚合成本，並把決策搬離發出它的那段程式碼。

**自由地加屬性，基數之後再說。** 「之後」是一張帳單，**與 ADR-0021 缺少成本保險絲時是同一種失效形狀**——一次昂貴的靜默失敗，而不是一次便宜的大聲失敗。
