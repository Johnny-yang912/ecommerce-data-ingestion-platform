# ADR-0055：增量窗口的邊界必須是分區邊界；回填傳日期，不傳天數

## 背景

[ADR-0046](./0046-stg-incremental-int-full-rebuild.md) 把 `stg_orders` 的增量正確性建立在一條不變式上：**同一個 `raw_id` 的所有副本都落在同一個 `received_at` 分區**，所以整分區原子覆寫不會留下漏網之魚。

那條不變式是真的，但它**只描述了窗內**。它保證「窗裡看得到的東西，去重會做完整」，對「窗的邊界切在哪裡」一句話都沒說。而 `insert_overwrite` 的原子單位是**整個分區**，dbt 只覆寫「查詢結果裡出現過的分區」——兩者相乘產生一個不變式管不到的失效：

> 左邊界若落在某天的**中間**，邊界那天就只有一部分的列進得了窗，於是 **`insert_overwrite` 拿半天原子覆寫整天**，窗外的列被靜默刪除。

原本的左邊界是 `timestamp_sub(current_timestamp(), interval N day)`——它帶著**跑批當下的時刻**。這讓「這支模型正確」變成一句條件句：只有在跑批時刻晚於當天最後一批資料抵達的時刻時才成立。例行排程是台北 22:30，seeding 最後一批的尾巴約 21:05，中間 85 分鐘的空隙就是這條管線唯一的安全邊際——**而它從來沒有被寫下來過，也沒有測試釘住。**

2026-08-29 20:38 的一次手動跑批落在那個空隙的錯誤那側，把 `2026-08-26` 分區從 800 列砍成 250 列（[事故報告](../incidents/2026-08-30-stg-partition-truncation.md)）。

同時，這條管線缺一個修復工具。當時唯一能重建舊分區的方式是**放大回看窗**——一個「從今天往回數 N 天」的參數，它繼承了同一個浮動邊界，而且要涵蓋一個舊分區就得連同它之後的每一天一起重算。

## 決策

**一、增量窗口的左邊界對齊日界。**

```sql
where received_at >= timestamp_sub(
    timestamp_trunc(current_timestamp(), day),   -- 這一層是正確性，不是風格
    interval {{ var('stg_orders_lookback_days', 3) }} day
)
```

邊界那天從此只有「整天在窗內」或「整天在窗外」兩種狀態。「半天」不再存在，**跑批時刻也就不再是正確性的隱含前提**。

**二、修復路徑以日期參數化，與時鐘無關。**

```bash
dbt run -s stg_orders --vars '{stg_orders_backfill_start: "2026-08-26"}'
```

`stg_orders_backfill_end` 可省略，省略即 `start` 當天。例行路徑不變，仍走滾動窗。

`_end` 刻意做成可省略：補單日卻把 `_end` 填成當天（而非隔天）會靜默選出空集合，而**回填是最不該留隱形陷阱的路徑**——出事時開指令的人往往不熟這條管線。

**三、逐分區對帳測試**守住這條契約。窗必須 **>** 回看窗。**每支增量模型各要一支**——見決策四。

**四、適用範圍＝所有 `insert_overwrite` + 時間窗的模型，不是只有 `stg_orders`。**

這條是 2026-08-30 補上的，因為第一次套用時漏了三分之二。當時的範圍是照「觀測到哪張表壞掉」劃的，而缺陷是**寫法**層級的——它的範圍等於「有多少地方照抄了這個寫法」，與「有多少地方已經出事」無關。

目前適用的三支，以及各自的守門測試：

| 模型 | 分區欄 | 對帳測試 |
|---|---|---|
| `stg_orders` | `received_at` | `assert_stg_orders_matches_staging` |
| `stg_quality_events` | `event_at` | `assert_stg_quality_events_matches_staging` |
| `rpt_quality_events_daily` | `event_date` | （上游兩支覆蓋；本身是聚合，無 1:1 對帳對象） |

⚠️ **對帳測試不可共用。** 每支測試只保護它自己指名的那一張表，**不能靠「另一支有測」推論這一支安全**——這正是 8/26 事件線掉列能在對帳測試已經存在的情況下活下來的原因。

**新增任何 `incremental` + `insert_overwrite` 模型時，這條規則與它的對帳測試一併適用。** 目前這件事靠 code review，沒有自動檢查——見〈後果〉代價五。

**五、上游回填舊分區後，下游增量模型必須用同一組日期跟著補。**

```bash
dbt run -s stg_quality_events   --vars '{stg_quality_events_backfill_start: "2026-08-26"}'
dbt run -s stg_quality_events+ --exclude stg_quality_events      # table 物化的下游會自動跟上
dbt run -s rpt_quality_events_daily --vars '{rpt_quality_events_backfill_start: "2026-08-26"}'
```

第三行不是多餘的。`stg_quality_events+` 會重建下游，但**下游的增量模型只重算自己回看窗內的分區**——被補的舊分區落在窗外，於是它照舊維持舊值。

> 失敗模式是最惡劣的那種：**上游正確、下游錯誤、所有測試全綠、BI 繼續顯示舊數字。** 2026-08-30 的修復就卡在這一步——`stg_quality_events` 已經是 800，Looker 讀的 `rpt_quality_events_daily` 仍然是 250。

## 這個右界為何不牴觸 ADR-0037

[ADR-0037](./0037-catchup-false-structural.md) 明確否決過一個右界：

> 真正的可補跑需要以 `received_at >= data_interval_start AND < data_interval_end` 切片……**那個右界會切掉遲到的列**

回填的 `_end` 也是一個右界。**兩者掛在不同的軸上：**

| | ADR-0037 否決的右界 | 回填的 `_end` |
|---|---|---|
| 界在什麼上 | 一次**排程 run 所擁有的時間區間** | `received_at`，一個**列的不可變屬性** |
| 誰決定它 | Airflow 的 `data_interval` | 修復的人 |
| 為何會切掉遲到的列 | 那個 run **只會發生一次**；區間關閉後才載入的列再也沒有 run 會去看它 | 不會——回填讀的是 staging **當下的全部內容**，晚載入的列 `received_at` 沒變，仍在同一分區 |
| 用在哪 | 例行路徑 | 只有修復路徑 |

關鍵差別是**一次性**：0037 否決的形狀把「這些列有沒有被抽到」綁在一個不會重來的 run 上。回填沒有這個性質——它是 ad hoc 的，可以再跑一次。

**這一節存在的唯一理由，是讓讀過 0037 的人不會誤以為這裡自相矛盾，或反過來把這個形狀誤用回 extract 層。**

## 後果

**跑批時刻從正確性條件裡消失了。** 手動跑、補跑、值班的人半夜跑，結果都一樣。這是最主要的收穫，而且它把一個「沒被寫下來的 85 分鐘空隙」換成了一個結構性保證。

**修復路徑不再有時間條件。** 修復發生在事故當下，而事故不挑時間。一個附帶「只在某某時段安全」但書的修復工具，在真正需要它的時候一定不能用。

**代價一：窗最多多含一天。** 對齊日界讓左界只會往**更早**移，不會往更晚。以現在每天約 800 列的規模可忽略；資料量成長後這是第一個要重估的地方。

**代價二：模型裡多了一條分支。** 例行路徑與回填路徑是兩段不同的 `where`，兩者會漂移。緩解是三條分支都由 `dbt compile` 驗過，且對帳測試不分路徑地守著結果。

**代價三：偵測窗是 7 天，不是無限。** 對帳測試把「掉列多久會被發現」從**永遠不會**推到**一天之內**，但只在 7 天窗內。超過 7 天才落地的遲到列（Proposal C 的形狀，見 ADR-0046）仍然無聲——那個缺口沒有被這條 ADR 關上。

**代價四：修復沒有自動的稽核紀錄。** 定點回填是一次 shell 呼叫——它修好資料，但系統不會留下「`2026-08-26` 曾經被補過」這件事。要回答三個月後的「這天的數字為什麼跟上游對不起來」，只能靠事故報告、CHANGELOG 與 git 歷史，**而那三者都倚賴人記得去寫**。

⚠️ 這個缺口的範圍比它聽起來窄：**紀錄靠人，偵測不靠人。** 下一次掉列會被對帳測試自動抓到並指出是哪一天、少幾筆——沒有人需要記得去跑它。人工的部分只有「補完之後把它寫下來」。

> **修正（2026-08-30 當晚）**：本節原本寫的是「下一次掉列會被 `assert_stg_orders_matches_staging` 自動抓到」。
> **那句話在寫下的當天就被推翻了。** 同一次跑批造成的 `stg_quality_events` 掉列，它一列都沒抓到——因為它只指名 `stg_orders`。
> 正確的陳述是：**對帳測試保護的是它指名的那一張表，不是「掉列」這個類別。** 覆蓋率等於「有幾支模型各自有一支測試」。

**代價五：「新模型必須套用這條規則」目前沒有自動檢查。** 決策四把適用範圍寫清楚了，但它仍然是一份需要作者去讀、去遵守的規則——**而這正是本 ADR 自己批評過的那種機制**（見事故報告〈教訓〉：一份寫成「要人記得」的檢查等於沒有這份檢查）。

誠實的現況：**這條規則現在靠 code review，不靠系統。** 已知的收口方式是把邊界抽成共用 macro（讓三份手寫變成一份定義），再加一條 CI 檢查——凡 `insert_overwrite` 模型未呼叫該 macro 即 fail，並保留顯式 opt-out 標記以維持彈性（opt-out 會出現在 diff 裡，手寫邊界不會）。專案已有同形狀的先例：`tests/test_dags.py` 就在對 DAG 原始碼做這類結構斷言。

**暫緩，不是否決。** 三支模型此刻全部一致且有測試守著，抽象化的收益要到第四支出現時才兌現；而把抽象化與資料修復綁在同一次改動裡，會讓「回填錯了」與「macro 寫錯了」無法分辨。條件記在 [PORTFOLIO_SCOPE #13](../PORTFOLIO_SCOPE.md)。

緩解是把「記錄下來」寫成 [dbt-ops runbook](../runbooks/dbt-ops.md) 的一個**步驟**，而不是一句期望。由系統自動產生這份紀錄的做法暫緩，條件記在 [PORTFOLIO_SCOPE #13](../PORTFOLIO_SCOPE.md)。

## 考慮過的替代方案

**`stg_orders` 改回全量重建。** 會讓這整類失效消失，而且以目前 14,587 列的規模成本趨近於零。否決的理由不是成本，是 [ADR-0046](./0046-stg-incremental-int-full-rebuild.md) 把 `stg_` 的增量當成「增量在此層是安全的」這個結論的展示——那個結論仍然成立，**它只是需要一個它原本沒說完的前提**。放棄增量會連帶刪掉那個展示。

**改用 `merge` 策略。** 這會從根本消掉整個類別：`merge` 按 `unique_key` 逐列合併，窗算錯只會「少更新」，**不會刪除**。兩者的失敗模式差一個等級。技術上不可行——BigQuery sandbox 禁止 DML，那正是逼出 `copy_partitions` 的同一條限制（[ADR-0044](./0044-copy-partitions-sandbox-dml.md)）。**啟用帳單後這是首選。**

**以 Airflow 的 `data_interval` 讓每個 run「擁有」它的分區。** 修復會變成「在 UI 上重跑那一天的 run」，稽核紀錄由 Airflow 自動產生。

**與已採方案的差別不在修復能力，在紀錄。** 兩者都能修好任意一個分區，也都與跑批時刻無關；差別是一個留下 run 歷史，一個留下一次 shell 呼叫。以單人操作、修復頻率極低而言，那份紀錄由人寫進事故報告與 CHANGELOG 反而更完整——它能寫下**為什麼**要補，那是 Airflow 的 run 歷史寫不出來的。

它另外要付的：每個 run 從此「擁有」一段區間，`catchup` 必須重新當成一個真的決策來想，DAG 與 dbt 之間多一層契約要維護。**那是拿複雜度換一份目前有人能手寫的東西。**

⚠️ 若把同一個形狀推廣到**例行路徑**（而不只是回填），還會撞上 [ADR-0037](./0037-catchup-false-structural.md) 否決右界的理由，而且理由在這一層同樣成立：一個 `received_at` 落在區間內、但在該區間的 run 跑完之後才載入 staging 的列，永遠不會有第二個 run 去看它。**滾動窗在例行路徑上是對的**，這一點沒有改變。

暫緩項與重啟條件記在 [PORTFOLIO_SCOPE #13](../PORTFOLIO_SCOPE.md)。

**只放大回看窗，不做定點回填。** 這是事故前的現狀。修好邊界之後它變安全了，但它仍然只能表達「從今天往回數 N 天」：要重建一個舊分區就得連帶重算其後每一天，而且開指令的人必須先自己把日期換算成天數。

## 何時重新檢視

- **啟用 BigQuery 帳單時**——改用 `merge` 並重估這條 ADR 是否還需要存在。
- **`int_` 層改成增量時**——同一條邊界規則必須一起套用（它會是第四個實例），且 ADR-0046 已記載它的重選集合更複雜（回看窗分區 ∪ 有品質事件的 `raw_id` 所屬分區）。
- **新增第四支 `insert_overwrite` 模型時**——代價五的抽象化（共用 macro + CI 檢查）在那個時點兌現收益，應重新評估。
- **資料量讓「多含一天」有感時**。
- **出現第二位操作者時**——代價四的人工紀錄從此不可靠，見 [PORTFOLIO_SCOPE #13](../PORTFOLIO_SCOPE.md)。
