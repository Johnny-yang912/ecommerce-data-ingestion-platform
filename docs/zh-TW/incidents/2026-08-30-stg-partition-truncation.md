# 半天的資料覆寫了一整天：`stg_orders` 靜默掉了 550 列

[English](../../en/incidents/2026-08-30-stg-partition-truncation.md) | **繁體中文**

| | |
|---|---|
| **日期** | 2026-08-29 20:38 發生 · 2026-08-30 10:20 發現 · 當日修復 |
| **影響** | `stg_orders` 的 `2026-08-26` 分區 800 列 → **250 列**；缺口傳播至 Gold |
| **告警** | **無**。DAG 綠、93 個 dbt 測試全綠、上游 staging 完好無損 |
| **偵測延遲** | 約 14 小時，且是**肉眼看 BI** 發現的 |

---

## 為什麼這份文件在這裡

本專案另外兩份事故報告的根因都在專案**之外**——一個編輯器擴充、一台開發機的時鐘。**這一份的根因是專案自己的一行 SQL。**

它也是三者中最難被看見的：沒有任何一個既有訊號離開綠燈，上游的原始資料一列都沒少，所以事後連「是誰刪的」都查不出來——被刪的列沒有留下任何痕跡。

---

## 症狀

Looker 上的營收曲線變矮，但**沒有任何一天整個消失**——缺口被抹開在約 45 個 `order_date` 上，看起來像雜訊而不是故障。

追進倉庫才看見它其實是單一一天的問題，而且問題不在那天：

| 層 | `2026-08-26` 的列數 |
|---|---|
| ODS（PostgreSQL） | 800 |
| `staging.orders`（BQ 鏡射） | 800 distinct `raw_id` ✅ |
| **`stg_orders`（Silver）** | **250** ❌ |

`2026-08-26` 當天的排程**完全正常**：四個 seeding 時段全部 success，Raw 狀態全是 `processed`。壞掉的是三天後的一次跑批。

掉得很有規律——只剩當天最後一個時段：

```
時段（台北）   staging   stg_orders
10:00           150    →     0     ✗
13:00           200    →     0     ✗
17:00           200    →     0     ✗
21:00           250    →   250     ✓
```

---

## 根因

`stg_orders` 的增量過濾原本是：

```sql
where received_at >= timestamp_sub(current_timestamp(), interval 3 day)
```

`current_timestamp()` 帶著**跑批當下的時刻**，所以左邊界會切在某一天的中間。而 `insert_overwrite` 的原子單位是**整個分區**——dbt 覆寫「查詢結果裡出現過的分區」，覆寫的內容就是查詢結果本身。

於是：

```
2026-08-26 分區：  |--02:00---05:00---09:00---13:00--|   共 800 列（UTC）
                      150      200      200      250

cutoff（2026-08-29 12:38 UTC 的跑批往回 3 天）  ↑ 12:38
窗內：                                            [========]   只剩 250 列
insert_overwrite 用這 250 列原子覆寫整個分區  →  其餘 550 列被刪除
```

觸發它的是 **2026-08-29 20:38 的一次手動跑批**（因為當晚要提早關機，把 22:30 的排程提前手動執行）。

**例行排程為什麼一直沒事**：台北 22:30 ＝ 14:30 UTC，而 seeding 最後一批的尾巴是 13:05 UTC。cutoff 落在 D-3 的 14:30，**晚於**當天最後一批 → 那個分區在查詢結果裡是**零列** → dbt 不碰零列的分區 → 完好。

> **這條管線的正確性一直依賴著 85 分鐘的時間差，而那個依賴從來沒有被寫下來，也沒有任何測試釘住它。**

危險窗是**台北 10:00–21:05**。手動跑批的 20:38 落在裡面。

**差 26 分鐘的第二次**：隔天 09:34 開機時，Airflow 補跑了前一晚錯過的 run。那次 cutoff 落在 `2026-08-27 01:34 UTC`，**早於**當天第一批（02:00 UTC），所以 8/27 整天都在窗內、被完整重寫。如果開機再晚半小時，8/27 會用同樣的方式再掉一次。

## 為什麼既有的防線沒擋住

| 防線 | 為什麼沒響 |
|---|---|
| DAG 狀態 | task 成功了。它**確實**完成了它被要求做的事 |
| 20 條 dbt 測試 | 全部問「這一列對不對」。活下來的 250 列每一列都完全正常 |
| Hard Gate | 逐批錯誤率。刪掉的列乾淨髒污比例正常，比率不動 |
| `source_freshness_watch` | 只看**最新一筆有多新**，不看**有幾筆** |
| [ADR-0044](../adr/0044-copy-partitions-sandbox-dml.md) 的 `copy_partitions` | 它擋住了「先刪後插」的中途失敗，**沒有擋住窗口邊界對不齊** |
| [ADR-0046](../adr/0046-stg-incremental-int-full-rebuild.md) 的同分區不變式 | 它保證窗**內**去重完整，對窗的**邊界**沒有任何主張 |

最後兩列是重點：**兩個既有的正確性論證都成立，只是都不涵蓋這個失效。**

### 它其實被預言過兩次

**一、** [`dbt_packages` 事故](./2026-08-dbt-deps-429.md)的〈教訓〉已經寫下這個形狀：

> 一個「先清空狀態、再去抓替代品」的工具，會把任何下載失敗變成資料遺失。那個模式值得普遍地辨認出來——**它與「在新資料被確認之前就刪掉分區」的 `insert_overwrite` 是同一個形狀**

當時的結論是 `copy_partitions` 已經處理掉它了。**那只處理掉一半。**

**二、** [`dag-failure-recovery` runbook](../runbooks/dag-failure-recovery.md) 的第 4 步「驗證沒有東西遺失」，內容正是逐分區比對 staging 與 `stg_orders` 的列數。

> **這個專案早就知道該做這項檢查。它只是被寫成一段「要人記得手動貼上去的 SQL」，而事故發生的那天，沒有人想到要跑它。**

---

## 鑑識過程

值得記下來，因為「上游完好」讓一般的追查順序失效——沒有錯誤訊息、沒有失敗的 task，唯一的線索是一個數字比預期小。

1. **逐層數列數**，從 ODS 往雲端數（800 / 800 / 250）→ 缺口夾在 staging 與 `stg_orders` 之間，也就是**在 dbt 裡**，不在抽取裡
2. **按小時拆**那 250 列 → 全部落在 13:00 UTC 那一批 → 不是隨機遺失，是**一刀切**
3. **從切點反推 cutoff** → `2026-08-26 12:38 UTC`
4. **在 `dag_run` 裡找 12:38** → 前一晚 20:38 的手動 run

第 2 步是轉折點：**隨機遺失指向去重或 join，一刀切指向一個過濾條件。**

---

## 處置

**一、根因**：左邊界對齊日界。

```diff
- where received_at >= timestamp_sub(current_timestamp(), interval N day)
+ where received_at >= timestamp_sub(timestamp_trunc(current_timestamp(), day), interval N day)
```

**二、修復路徑**：新增 `stg_orders_backfill_start` / `_end`，用日期指定分區，與跑批時刻無關。

**三、偵測**：新增 `assert_stg_orders_matches_staging`，逐分區比對 staging 的 `distinct raw_id` 與 `stg_orders` 的列數。窗 7 天（**必須 > 回看窗**）。

決策記錄於 [ADR-0055](../adr/0055-partition-aligned-incremental-window.md)。

### 資料修復

在台北 11:24 執行——**舊危險窗的正中間**，這本身就是修復路徑不再有時間條件的證明：

```bash
dbt run -s stg_orders --vars '{stg_orders_backfill_start: "2026-08-26"}'
dbt run -s stg_orders+ --exclude stg_orders
```

| | 修復前 | 修復後 |
|---|---|---|
| `stg_orders` 的 8/26 分區 | 250 | **800** |
| `stg_orders` 總計 | 14,037 | **14,587** |
| `fct_orders` | 12,935 | **13,434**（+499） |
| `int_orders_quarantine` | 986 | **1,037**（+51） |
| 對帳測試 | FAIL | **PASS** |
| dbt 測試全套 | — | **94 / 94 PASS** |

`499 + 51 = 550`。乾淨的進 Gold、髒的進隔離區，比例與該批資料原本的髒率一致——它們是**照正常規則重跑**的，不是被硬塞回去的。

`14,587 − 13,434 − 1,037 = 116`，與修復前完全相同：那是 `order_date` 60 天分區過期的已知議題，未受這次重建影響。

> 對帳測試**先紅後綠**：修復前它吐出 `2026-08-26 / 800 / 250 / 550`，修復後轉綠。**只會綠的測試等於沒有測試。**

> **這次回填的紀錄就是這份文件本身。** 那是目前的機制：紀錄靠人寫，不靠系統產生——[PORTFOLIO_SCOPE #13](../PORTFOLIO_SCOPE.md) 記錄了為什麼暫時如此，以及什麼條件下會改。

## 附帶發現：補跑不保證 DAG 之間的時序

調查期間順帶查明的一件事，已自癒、無需處置，但值得記下。

`orders_analytics_daily` 的檔頭記載了一個時序契約：seeding 最後一批（21:00）到抽取（22:30）之間有 84 分鐘餘裕。**那個契約只存在於排程時刻表裡。**

2026-08-30 開機時，四支 DAG 的補跑在**同一秒**（01:34:44 UTC）全部湧出，於是抽取跑在 seeding 還沒灌完的當下——當天 ODS 有 399 列，只抽到 **4** 列。

它會被下一輪 `>=` watermark 自動補回（[ADR-0023](../adr/0023-watermark-approach-a.md)），所以不需要處置。但**判讀時要知道**：`catchup=False` 不是「不補跑」，它補最近一個錯過的區間，而且補跑時 DAG 之間沒有任何排序。

## 教訓

> **一個讀自己時鐘的批次模型不是冪等的。** 同一支模型、同一份程式碼，在 20:38 與 22:30 跑會產出不同結果——這就是缺陷的本體，「3 天寫成了 3×24 小時」只是它的表徵。

> **能被內容測試抓到的前提，是那一列還在。** 20 條測試問的都是「這個值對不對」，沒有一條問「列還在不在」。一個只做內容測試的測試套件，在資料被刪掉時是全綠的。

> **一份寫成「要人記得去跑」的檢查，等於沒有這份檢查。** 那段 SQL 三個月前就寫進 runbook 了。它的內容完全正確，代價是它需要有人在正確的日子想起它。

第四點是關於這次為什麼有得救：**`staging` 是 append-only 而且沒有被動過。** 那不是這次修好的東西，是這次唯一沒有壞掉的東西——**它才是讓 550 列可以完整還原的唯一原因**（[ADR-0025](../adr/0025-staging-additive-only.md)）。不可變的上游是一個成本，直到你需要它的那一天。
