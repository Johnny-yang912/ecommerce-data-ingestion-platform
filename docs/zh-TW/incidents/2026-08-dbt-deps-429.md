# `dbt_packages` 被清空，`dbt deps` 報 "not a gzip file"

[English](../../en/incidents/2026-08-dbt-deps-429.md) | **繁體中文**

| | |
|---|---|
| **日期** | 2026-08 |
| **影響** | 排程的 dbt task 變紅；`dbt_packages/` 間歇性地空掉 |
| **根因** | 編輯器擴充在背景重複執行 `dbt deps`，撞上 codeload 的速率限制 |
| **狀態** | 已查明；藉由關閉那個自動行為緩解 |

---

## 症狀

兩個看起來不相關、實際上相關的症狀：

1. **`dbt_packages/` 是空的**，所以每一個引用 `dbt_utils` 的 model 都編譯失敗。
2. **`dbt deps` 以 `not a gzip file` 失敗**——一則令人困惑的錯誤，因為這個指令跟使用者選擇的任何壓縮都無關。

由於排程的 DAG 會跑 `dbt build`，這件事浮現的樣子是**一條紅掉的分析管線**，配上一則指向不了任何有用方向的錯誤訊息。

---

## 根因

VS Code 的 dbt 擴充**會在背景自動執行 `dbt deps`**——存檔時、開啟專案時，以及其他使用者無法控制的觸發點。

`dbt deps` 從 GitHub 的 `codeload` 端點下載套件。短時間內夠多次的自動呼叫，codeload 就會回 **HTTP 429（速率限制）**。

接著失效以一種特定的方式複合：

```
dbt deps 開始
  → 先清空 dbt_packages/
  → 從 codeload 下載
  → codeload 回 429 —— 一個 HTML／文字的錯誤內容，不是 tarball
  → dbt 把那份內容寫到磁碟並嘗試解壓
  → "not a gzip file"
  → dbt_packages/ 被留在【空的】狀態
```

**破壞性的那一步發生在脆弱的那一步之前。** 那正是為什麼目錄最後是空的而不是過期的：下載失敗時，舊的套件早就已經不在了。

---

## 為何它令人困惑

| 你看到的 | 為何誤導 |
|---|---|
| `not a gzip file` | 暗示壓縮檔損壞或磁碟問題。實際上是一個 HTTP 錯誤內容被拿去解壓 |
| 間歇性 | 取決於擴充最近觸發了幾次——只有在速率限制下才重現得出來 |
| 沒有人執行過 `dbt deps` | 呼叫來自編輯器而非終端機，所以它不在 shell 歷史裡 |
| DAG 是紅的，但手動跑 dbt 正常 | 等你手動去試的時候，速率限制已經過期了 |

最後一列是其中最糟的：**手動重現會成功**，而那會把調查引離真正的成因。

---

## 處置

1. **關閉擴充的自動 `dbt deps`。** 手動呼叫沒問題；製造出爆量的是自動那個。
2. **等速率限制過去之後，手動跑一次 `dbt deps`** 把 `dbt_packages/` 還原。
3. **不要把 `dbt_packages/` 進版控**——它是產生物，而為了閃避這件事去 vendor 它，等於用一個暫時性的失敗換一份永久的維護負擔。

---

## 教訓

> **一個「先清空狀態、再去抓替代品」的工具，會把任何下載失敗變成資料遺失。**

那個模式值得普遍地辨認出來——它與「在新資料被確認之前就刪掉分區」的 `insert_overwrite` 是同一個形狀，**而那正是 `copy_partitions` 用「對一份完成的複製做 `WRITE_TRUNCATE`」而非「先刪後插」的原因**（[ADR-0044](../adr/0044-copy-partitions-sandbox-dml.md)）。

第二個教訓是關於歸因：**一個不是你呼叫的背景行程，仍然是你的依賴。** shell 歷史是乾淨的，所以調查一開始假設是網路或套件庫的問題。
