# 排程靜默停擺：四次事故與一次架構遷移

[English](../../en/incidents/2026-08-silent-scheduling-stalls.md) | **繁體中文**

| | |
|---|---|
| **期間** | 2026-08-11 ~ 2026-08-14（退路收尾至 08-17） |
| **影響** | 分析管線四次停擺，最長單次 13 小時 22 分；期間無資料進入 BigQuery |
| **告警** | **四次皆無**。所有既有監控指標在停擺期間維持綠燈 |
| **狀態** | 已結案。三項根因未查明，處置與代價記錄於文末 |

## 為什麼這份文件在這裡

這四次事故發生在開發主機的環境層（WSL2、Docker、Windows 開機流程），不在應用程式碼裡。單看成因，它們確實是本機問題。

但它們留下的東西不是本機專屬的：

- **失效模式可推廣**——「沒有任務被建立，就沒有失敗可看，監控自然全綠」在任何排程系統上都成立
- **它是三個設計決策的直接輸入**——`raw_pending_watch` 這個 DAG、探針閾值的推導方式、以及存活告警的設計原則，全部源自這裡

換句話說，這份文件記錄的不是「我的電腦壞了」，而是**「我用來判斷系統健康的標準錯了，以及我怎麼修正它」**。後者屬於這個專案。

## 共同結構：為什麼四次都沒有告警

停擺期間，以下七個指標全部正常：

| 指標 | 停擺時的實際值 | 它證明了什麼 |
|---|---|---|
| 容器狀態 | `Up` | 行程存在 |
| 重啟次數 | `0` | 沒有崩潰迴圈 |
| 容器錯誤欄 | 空 | 沒有啟動失敗 |
| 應用 log | 乾淨 | 沒有例外被拋出 |
| DAG 列表 | 列得出來 | **（假訊號）**讀的是資料庫殘留，不是當前解析結果 |
| Scheduler 心跳 | 零斷層 | 主行程還在跑 |
| 健康檢查 | 存活 | 連接埠有回應 |

**七個指標的共同點：它們全都在證明「東西還在」，沒有一個在證明「東西有在工作」。**

這就是這次事故序列最核心的產出——**存在性訊號（liveness）不等於進展性訊號（progress）**。排程器可以完整地活著、心跳、回應健康檢查，同時十三個小時不建立任何一筆排程。

## 事故一 — 時鐘漂移

### 現象

排程時間到了，DAG 沒有跑。Airflow 完全不報錯，沒有 import error，手動解析 DAG 檔案只需一秒且零錯誤。六個 DAG 全部標記為 `stale`，最後一次成功解析停在數小時前。

### 根因鏈

```
WSL2 kernel tick 被壓低約 3.6%
  → 系統的 MONOTONIC 時鐘相對 MONOTONIC_RAW 持續落後
  → 另一個對時服務又反向修正，兩個控制器互相打架
  → DAG 解析子行程一生出來，就被判定「已逾時數百秒」而遭砍
  → DAG 永遠解析不完 → 永遠 stale
  → 排程器不對 stale 的 DAG 建立 run
  → 沒有 run 就沒有失敗，沒有失敗就沒有紅燈
```

### 排查關鍵

**不要追 DAG 程式碼。** 手動解析只要一秒且零錯誤，這個事實本身就排除了語法與 import 問題，卻很容易被忽略。

實際有效的三步：

1. 比對兩種時鐘（`MONOTONIC` vs `MONOTONIC_RAW`）——正常應幾乎相等
2. 量測自開機起的累積偏移總量——這才是撞牆的那個量
3. 拿主機時間當外部基準——實測與 `MONOTONIC_RAW` 完全一致，可當真值

### 處置與代價

把 DAG 解析容忍度拉長 72 倍，並停掉打架的那一方（停用前先確認沒有其他程式依賴它）。

**這是買時間，不是修好。** 根因未解，但代價可以計算：

```
撐住時間 = 容忍度 ÷ 漂移率
```

每日關機會重置累積量，所以目前的使用模式撞不到上限；換成 24 小時常駐的機器，約 27 小時後會再次撞牆。**知道自己買了什麼，比假裝解決了重要。**

已排除的做法：直接把 tick 值寫回去——kernel 每 8 秒覆寫一次，兩分鐘內就被蓋掉。

## 事故二 — 開機掛載競態，以及由此導出的架構遷移

這是四次裡唯一導致架構變更的一次，也是方法論產出最多的一次。

### 現象

主機重開後，Airflow 全滅。容器狀態 `Exited (127)`，而 `docker logs` **看不到任何東西**——因為失敗發生在容器建立階段，根本還沒產生 log。錯誤只存在於容器的 `State.Error` 欄位。

### 根因

主機重開後，容器還原跑在檔案系統可用之前。掛載來源解析不到時，**Docker 不報錯，它給你一個空的**——bind mount 靜默退化成 tmpfs。

而且失敗發生在建立階段，容器從未進入 running 狀態，**所以重啟策略不會接手**，healthcheck 也不會觸發修復。

### 第一次處置的方向是反的

第一版修法是把單檔掛載改成目錄掛載，讓來源在開機當下總是存在。

結果：**指標全部變好看了，管線停擺一模一樣。**

原本是吵鬧的失敗（`Exited 127`，至少看得見），被換成了安靜的空目錄（容器 `Up`，掛載內容是空的）。這次失敗留下一條判讀反轉：

> **容器全部 `Up` 不代表沒中獎。** 必須進到容器裡檢查 mount type——出現 `tmpfs` 就是中獎，正常應該是 `ext4` 或 `virtiofs`。

### 零足跡實驗推翻了已排好的實作計畫

第一次修法失敗後，排出了一套七步的後續修法。這七步全部建立在同一個假設上：

> **「掛載壞掉的容器，重啟一次就會重新掛上。」**

在動手之前，先用免洗容器做了五組對照實驗（A–E），全程不碰任何進版控的檔案。

**那個假設是錯的。** 掛載對映是在**容器建立時**登記的，`start` 不會重新登記。壞掉的容器重啟一萬次也一樣壞，唯一的修法是強制重建。

那七步，一步都沒有做。

> **判斷依據**：五組免洗實驗約二十分鐘、零副作用；七步實作要修改三個進版控的檔案，錯了要回退、要重新 review。前提為真的信心不到八成時，驗證就是划算的。

### 從「修競態」到「消除競態的前提」

第二次面對這個問題時，沒有直接採用處置方案，而是先要求把**成因**講清楚。

推導出的空窗形狀是：

```
開機登入
  → Docker 啟動
  → 此時 WSL 尚未啟動
  → Docker 抓不到它依賴的環境
  → 掛載來源解析失敗 → 靜默退化成空的
```

拿這個成因去對照一個已知不會出事的參照系：

> **原生 Linux 環境根本不會有這段空窗**——Docker 和檔案在同一個系統裡，不存在「等另一個系統起來」這件事。

由此反推出的結論是：**那段空窗不是 Docker 的問題，是「Docker 在系統 A、檔案在系統 B」這個前提造成的。**

所以最後的動作不是修掉競態，而是**消除競態存在的條件**——把 Docker 從 Windows 側的 Desktop 整合，遷移成 WSL 內部的原生 Docker Engine。

這個推理形狀是可重複的：

> **拿一個已知不會出事的參照系，反推出哪個前提是多餘的。**

**方法上的一點**：修法可以照做，成因不能照做。要求成因，等於強迫自己拿到能繼續往下推的原料——如果直接照著修法動手，就會一直待在「怎麼修好這個競態」的問題框裡。

### 驗收與遷移代價

十項驗收，其中最硬的一項：

> **完整重開機一次，全程不手動下任何啟動指令，服務要自己起來、掛載型別要正確。**

配套：舊環境完全不解除安裝當退路、舊資料先不清。

十項全過的當下**刻意不宣告結案**，理由是只跑過一次開機循環，而開機競態是間歇性的，單一樣本不構成證據。

**這個判斷後來被證明是對的**——事故三就發生在觀察期內。

退路在五天後（08-17）確認穩定才收掉，一併回收 18 GB 磁碟空間。

## 事故三 — 開機自動化「成功」，但環境活不久

### 現象

開機自動化任務回報成功（回傳碼 `0`），但登入 15 分鐘後檢查，容器根本不存在。

### 根因

叫醒 WSL 的命令一返回，distro 就被回收。第一版用的命令只活了 **1 秒**。

第一次修法後延長到 **1～5 分鐘**——這比原本**更難察覺**，因為它足以騙過大部分的手動檢查。

### 處置

兩個地雷必須同時處理，只修一個症狀幾乎一樣：

1. 改用長駐錨點，讓命令維持存活直到 docker 就緒才返回
2. 解除排程任務的執行時限

### 副產物：健康判準反轉

修法之後，**原本代表成功的回傳碼 `0`，現在代表錨點死了**。健康的狀態反而是任務仍在執行中的回傳值。

這是這次事故序列裡第二次判讀反轉（第一次是事故二的「容器 Up 不代表掛載成功」）。

## 事故四 — 睡眠回復後的殭屍排程器

### 現象

機器從睡眠回復後，排程器**同一個行程**醒來，但整整 13 小時 22 分不建立任何排程。

心跳零斷層、beat 正常、容器數正確、健康檢查回報存活——**全綠**。

### 排查

唯一可靠的訊號是：**排程紀錄表裡有沒有新的 row**。心跳、容器狀態、健康檢查全部測不到這件事。

第一輪判斷認為這是睡眠模式本身的問題，方向是改腳本讓環境在睡眠回復後能繼續使用。這個方向沒有被採用——改為把整條鏈攤開重驗：

> 遷移了 Docker、寫了開機腳本讓環境自動拉起、Docker 自動起服務——這條鏈對嗎？現在是哪一環沒被走到？

答案是：**鏈是對的，這台機器根本沒有重開過。**

再追一層——「確實按了關機，那『重新啟動』差在哪？」——才查出 Windows 的開機類型差別：**快速啟動讓「關機→開機」變成混合式休眠，不是冷開機**。先前所有的「冷啟動驗證」都沒有真的走到那條路徑。

### 處置與未解

關掉快速啟動，讓關機真的是冷開機。

**殭屍的根因至今未查明。** 後續的穩定是移除了觸發條件，不是修好了它。

## 判準的三次修正

這次事故序列裡，比任何單一修復更重要的產出，是**用來判斷「排程還活著」的標準本身被推翻了三次**。

| 版本 | 判準 | 被什麼推翻 |
|---|---|---|
| v1 | 心跳是最便宜的存活證據 | 事故四。殭屍狀態下心跳完全正常 |
| v2 | 只看有沒有真的建立排程紀錄 | 當晚驗證。**窗口內本來就沒有排程點時，空紀錄什麼都不能證明** |
| v3 | 先確認窗口內確實有一個該產生的排程點；沒有就手動觸發一個唯讀探針 | 目前有效 |

**v3 為什麼有效**：手動觸發會寫入一筆排隊中的紀錄，並把它推進到執行、派工、回寫成功——這整段都是排程器主迴圈的工作，正是殭屍狀態下卡死的那一段。心跳測不到這段，而探針一秒多就能拿到決定性答案。

## 這些教訓變成了系統裡的什麼

這是這份文件屬於本專案的理由：

| 事故留下的判準 | 落實成什麼 |
|---|---|
| 存活訊號 ≠ 進展訊號 | **`raw_pending_watch` DAG**——不看行程活著，看「有沒有訂單卡在未認領狀態」。見 [ORCHESTRATION §2.12](../design/orchestration.md) |
| 沒有排程點時，空紀錄不是證據 | 探針閾值由**恢復路徑自己的設定推導**，而非寫死一個數字 |
| 綠燈可能是假的；相信自己有告警比沒有告警更危險 | **失敗通知的訊息寫「該做什麼」而非任務名**，且每則訊息都帶 `channel=`，`channel=log` 明示沒有人被通知。見 [ORCHESTRATION §2.13](../design/orchestration.md) |
| 判準必須能被自己推翻 | **存活告警的設計原則**——包含一個反直覺結論：cumulative temporality 下序列永不 absent，所以 `absent()` 抓到的是「行程死了」而非「上游停了」。見 [ORCHESTRATION §4.1](../design/orchestration.md) |
| 動版控檔案前先用零成本實驗測掉關鍵假設 | 成為此專案處理環境層變更的預設做法 |

## 結案狀態

### 已驗證（2026-08-14，整日無人值守）

- 5 個排程點誤差皆 < 1 秒
- 16 個 task 全部 success
- 當日 800 筆訂單準時進入雲端
- 93 個 dbt 資料品質測試全綠

### 仍未解決（三項）

1. **時鐘漂移的根因未查明。** 處置是拉長容忍度 72 倍，代價已量化（常駐機器約 27 小時後失效）。
2. **睡眠殭屍的根因未查明。** 處置是移除觸發條件（關閉快速啟動），非修復。
3. **「排程器根本沒在跑」的監控盲點仍在。** 補法已知（liveness 規則），但閾值需要真實流量才有意義——這屬於刻意暫緩，見 [PORTFOLIO_SCOPE](../PORTFOLIO_SCOPE.md)。
