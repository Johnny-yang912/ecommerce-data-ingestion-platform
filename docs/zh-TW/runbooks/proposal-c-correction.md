# Runbook：從 Raw 批次修正被洗壞的歷史值（Proposal C）

[English](../../en/runbooks/proposal-c-correction.md) | **繁體中文**

---

## 何時適用

三個問題全是「是」，才是這裡：

| 問 | 若「否」 |
|---|---|
| `raw.status` 是 `processed`？ | → `POST /process_raw/{id}?force=true`（路徑 A） |
| 錯的是**值**，不是判定？ | → [proposal-b-rollout](./proposal-b-rollout.md)（路徑 B） |
| Raw payload 裡的原始值還是對的？ | → 救不回來，[quarantine-writeoff](./quarantine-writeoff.md) |

典型長相：清洗規則的 sentinel 清單把 `"na"`（North America）誤當成空值，過去三個月 8,000 筆訂單的 region 被洗成 NULL。**管線沒失敗、規則沒誤判、值錯了。**

---

## ⚠️ 這不是一份現成程序

Proposal C 是**被設計、未實作**——底下要用到的零件一個都還沒建。這裡寫的是「一旦要做，必須照這個順序」，不是今天能跑的腳本。

刻意不做成 HTTP endpoint、也不做成 DAG——與 `permanently_rejected` 同一份紀律：

> **不可逆的決定不該有方便的按鈕。**

**這也是 [README](./README.md) 那條「不要修改 ODS」唯一的合法逃生口。** 被禁止的是「單筆、無版本、下游不知情」的改寫。批次、有版本、留退役副本、強制連動下游的修正，是這一份。

---

## 兩種形態

第 0～2 步與第 4～6 步兩種形態完全一樣，分岔只在第 3 步——**修正值落在哪裡**：

- **遷移形**：在主表原地替換，舊的列搬到備份表。修完之後主表就是唯一真相。
- **補丁形**：主表完全不動，修正值寫進另一張表，讀的時候疊上去。

**選哪一個不在這裡決定。** 帶著第 1 步得到的數字，回 [design/data-quality](../design/data-quality.md#c-1-兩種形態) 的比較表與裁量清單。

---

## 第 0 步：先修程式，再碰資料

把造成問題的清洗邏輯改掉，部署上去。

今天不修程式就去補資料，明天新進來的訂單還是會被洗壞——災區會一直往右長，永遠補不完。**先部署，災區的結尾才會凍結在部署那一刻**，你才有一個有頭有尾的固定範圍可以處理。

---

## 第 1 步：圈出災區

只是查詢，不動任何東西，隨時可以重做。

**唯一的陷阱是用哪個時間欄位。** 要用 `ods.received_at`（這筆資料什麼時候被產出），不能用 `raw.received_at`（payload 什麼時候送進來）。有些訂單是半年前送進來、當時卡住、上個月才被恢復掃描重新處理——它的值產於災期，但送進來的時間在災期外。用送進來的時間去圈，這些會漏掉。

```sql
select id, raw_id, order_id, received_at, <被洗壞的欄位>
from ods
where received_at >= '<災期起>' and received_at < '<災期迄>'
  and <辨識被洗壞的條件>;
```

做完你手上有四個數字：**哪些訂單、哪個欄位、幾筆、日期範圍從哪到哪。** 後面每一步都要用，決策閘也要用。

---

## 第 2 步：重算，但先不寫

拿每一筆的 Raw payload，用修好之後的邏輯重算。

**不是重跑整條管線，只借用兩個純函數：`from_nested` → `clean_order`。** 正常入口 `process_raw_event` 有一道 first-write-wins 預檢——它會看到 ODS 裡已經有這個 `order_id`，把你正要替換的那一筆判成 `duplicate`，整批當場報廢。你做的是替換，不是重新攝入，所以必須繞過正門。

**呼叫時必須把該筆原本的 `received_at` 當作 `as_of` 傳進去。** 不傳的話，跟時間有關的規則會依「現在」重新判斷——那是重新判斷，不是重算（見 `clean.py` 中 `clean_order` 的 docstring）。

`clean_order` 這一次呼叫同時回傳**修好的值**和**對新值的品質判定**——第 3 步要寫的品質事件，內容就是這裡免費拿到的，不需要再算第二次。

**算完先不要寫。** 輸出一份對照給人看：

```
raw_id  order_id   欄位      舊值    新值
1234    ORD-0001   region    NULL    na
...
共 8,000 筆
```

順便斷言每一筆的 `raw_id` 在 `raw` 裡都還找得到——外鍵本來就會擋，但在這裡先抓到，可以避免一個做到一半的 runbook。

**到這裡為止隨時可以收手，什麼都還沒發生。**

## ⚠️ 決策閘——人的決定

帶著第 1 步的數字，去 [design/data-quality](../design/data-quality.md#c-1-兩種形態) 選定形態，並**把理由寫下來**（第 6 步會用到）。

這裡不給預設答案。事故當下的規模、下游消費狀況、有沒有運維窗口，都會改變答案。

## 動手之前要先建的零件

| | 遷移形 | 補丁形 |
|---|---|---|
| 共用 | 批次編號（`reprocess_batches` 表）——它同時是雲端去重的決勝鍵，**不只是稽核欄位** | 同左 |
| 表 | `ods.rebuild_batch_id` 欄位、`ods_retired_<批次>` 備份表 | `ods_corrections` 表（`raw_id` 比照加外鍵） |
| 抽取 | 無（複用既有通道） | 自己的 `FIELDS` 宣告、抽取邏輯、與 `test_schema_bq_consistency` 同級的守衛 |
| 其他 | 覆寫 `statement_timeout` 的專用連線；`stg_orders.sql` 的去重決勝鍵要把批次編號排到最前 | 讀取端的 overlay 疊加邏輯與批次優先序 |

備份表**不可繼承外鍵**（用 `LIKE ... EXCLUDING CONSTRAINTS`），否則備份副本會把 raw 的列釘住。

> **逐列的痕跡是 `rebuild_batch_id`，不是品質事件。** 每一筆修正列都帶著它，一筆不漏；`quality_events` 只記「品質判斷變了」的那些（見下一步）。兩份日誌、兩條軸，不互相代班。

---

## 第 3 步（遷移形）：一次交易，四件事一起

**這是不可逆點。** 開一個 transaction，裡面做四件事：

1. 把災區那些**舊的**列原封不動複製到 `ods_retired_<批次>`
2. 從主表刪掉那些舊列
3. 把重算後的新列寫回主表，每一筆帶上批次編號
4. Append 品質事件（內容用第 2 步算出來的判定）

**四件事不能拆開。** 假如第 3 件成功、第 4 件失敗，你會得到一批「值換掉了、但品質狀態機不知道」的資料——下游判斷誰該被隔離時，依據的狀態跟實際的值對不起來，**而且不會有任何東西報錯**。備份若單獨先做，中間掛掉就留下一份沒人知道該不該用的孤兒副本。要嘛四件全成功，要嘛四件都沒發生。

**關於第 4 件事**：它不是人去打 SQL。跟攝入時同一個模式——資料和事件在同一個 commit 裡由程式一起寫，差別只在誰按下執行鍵。

**事件寫什麼**：沿用既有的 `promotion` / `re_quarantination`，並且**只在狀態真的改變時 append**（與攝入層同一條規則）。這次修的是我方造成的值缺陷，規則沒有動，所以本來乾淨的還是乾淨、本來髒的還是髒，多數列的狀態根本沒變，不寫事件是正確的——事件表本身就是冪等閘。真正會產生事件的是「被洗壞而觸發規則、修好後值回來了」（`promotion`）與較罕見的反向（`re_quarantination`）。批次編號記進 `reason`。

**寫法上參照 `reevaluate_quality.py` 的 `fetch_current_states()` 與 `decide_target_state()`——參照，不是 import。** C 是獨立腳本；B 的判斷邏輯不該為了 C 長出例外參數，否則日後動 B 的規則會靜默改到 C 的行為，而 C 是幾年才跑一次、沒人記得的路徑。參照時有兩點必須一起帶走：

1. **決勝鍵必須是 `(event_at, id)`**，與 `int_` 層的 `order by event_at desc, id desc` 一致。不一致的話，C 會基於一個 Gold 看不到的狀態做決定，而且不會報錯。
2. **`NON_REPRODUCIBLE_CODES` 那條封鎖不適用於 C。** B 把它視為「不通過」，是因為 B 的輸入是已被正規化的 ODS 值，通過等於證據消失。**C 的值是從 Raw 重產的——證據回來了**，C 正是唯一能解除那個封鎖的機制。照抄 B 的判斷會把該救的列全部靜默跳過。

另外，全域的 30 秒 SQL 逾時是為線上短交易設的，會砍掉上萬列的批次——這條連線必須自行覆寫。

> **回滾**：反向再做一個批次，從備份表蓋回去。同一套機制自我支撐，不需要另一條路徑。

---

## 第 3 步（補丁形）：寫進另一張表，主表不動

把重算後的值寫進 `ods_corrections`，帶上批次編號；品質事件的處理與遷移形完全相同（同一個 transaction、同樣只在狀態改變時寫、同樣參照而非 import）。

主表從頭到尾沒被碰過，所以**沒有不可逆點**——要撤銷就作廢這一批修正。

代價是真相從此分裂在兩張表：**正確的值 = 主表 ⊕ 修正表**。這條縫是常駐的，不是一次性的：

- 同一筆被修正兩次時，疊加順序要自己實作（遷移形由主表天然解決）
- **任何一次 staging 全量重抽之後，都必須記得重推修正**——否則錯值復活
- 「讀 ODS 必須套 overlay」變成一條新的隱性契約，需要文件與守衛，防止未來的人直讀主表

---

## 第 4 步：手動把修正推上雲

雲端抽取靠一個只往前看的指針：每次只撿比上次更新的資料。而修正列**刻意保留了原本的舊時間戳**（它代表的還是那筆訂單當初的時刻，改掉就說謊了）。

結果是那個指針**永遠看不到這些列**，等多久都不會自己上去。這一步必須人主動推。雲端側細節見 [design/cloud-layer](../design/cloud-layer.md)。

---

## 第 5 步：叫下游重算那幾個舊分區

資料進了 BigQuery 的 staging，但下游模型也是增量的、每天只算最近幾天。修正列落在三個月前的分區，例行跑批同樣看不到。

```bash
dbt run -s stg_orders --vars '{stg_orders_backfill_start: "<最早的修正日>", stg_orders_backfill_end: "<最晚日 + 1>"}'
```

**用日期，不要用天數**（見 [dbt-ops](./dbt-ops.md#proposal-c-的定向刷新)）。若品質事件也落在舊分區，`stg_quality_events` 與 `rpt_quality_events_daily` 要用同一組日期跟著補。

> ⚠️ **第 4 步和第 5 步是綁死的一對。** 只推不刷，PostgreSQL 已是新值、Gold 還是舊值，**而且沒有任何東西會變紅**。這是整條流程最危險的收尾方式：做了一半，而且看起來很成功。

---

## 第 6 步：寫下來

系統不會留下「這批資料被人工改過」的痕跡。三個月後有人問「這天的數字為什麼跟上游對不起來」，只有這份紀錄答得出來。

最小集合：**哪個範圍 · 之前幾列 · 之後幾列 · 為什麼修 · 選了哪個形態、為什麼。** 寫進 `docs/zh-TW/incidents/`。

## 驗證

| 檢查 | 預期 |
|---|---|
| 修正後的值出現在 `fct_orders` | 是 |
| 舊的錯值不在任何 Gold 表 | 是 |
| 狀態有變的那些列，`quality_events` 有對應事件且 `reason` 帶批次編號 | 是 |
| 狀態沒變的那些列，**沒有**新事件 | 是——只在狀態改變時寫 |
| 重跑同一批修正 → 寫入 **0** 筆品質事件 | 是（冪等，同 [proposal-b-rollout](./proposal-b-rollout.md) 步驟 7） |
| （遷移形）`ods_retired_<批次>` 筆數 == 災區筆數 | 相等 |
| （補丁形）全量重抽的 runbook 已補上「重推修正」這一步 | 是 |

## 絕不可做的事

| 不要 | 為何 |
|---|---|
| 走 `process_raw_event` 重跑 | first-write-wins 預檢會把要替換的那一筆判成 `duplicate`，整批報廢 |
| 把第 3 步拆成好幾個 transaction | 留下「值換了但狀態機沒記錄」的裂縫，而且不會報錯 |
| 推上雲之後不做定向刷新 | PG 與 Gold 永久分歧，全綠 |
| 用 `raw.received_at` 圈災區 | 漏掉被恢復掃描較晚重新處理的那些列 |
| 重算時不傳 `as_of` | 時間相依的規則會依「現在」重判——那是重新判斷，不是重算 |
| 直接 import `reevaluate_quality.py` 的判斷函數 | B 會為了 C 長出例外參數；日後改 B 的規則會靜默改到 C |
| 讓備份表繼承外鍵 | 備份副本會釘住 raw 列 |
