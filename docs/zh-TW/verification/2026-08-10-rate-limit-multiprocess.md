# 2026-08-10 — 跨多行程的限流

[English](../../en/verification/2026-08-10-rate-limit-multiprocess.md) | **繁體中文**

---

## 驗證的假設

把恢復掃描搬出 API 行程（ADR-0016）之後，API 得以跑多個 uvicorn worker。**API 裡還有其他東西持有行程內狀態嗎？**

slowapi 預設把限流計數器放在行程記憶體裡。問題是那會不會有影響。

## 環境

api 跑 **4 個 uvicorn worker**。`POST /orders` 的限流設為 `60/minute`，以已驗證的 `client_id` 為鍵。2026-08-10。

## 方法

用**同一把 API key** 送 100 個 `POST /orders`，計算回應。

跑兩次——一次計數器在行程記憶體（`RATE_LIMIT_STORAGE_URI=` 留空），一次指向 Redis db 1。

## 觀測

| 計數器儲存 | `200` | `429` |
|---|---|---|
| 行程記憶體 | **91** | 9 |
| Redis db 1 | **60** | 40 |

## 結論

計數器在行程記憶體時，`60/minute` 實質上是 **`60 × workers`**。觀測到 91 而非乾淨的 240，只是因為請求沒有平均分配到四個 worker——**移動的是上限，不是算術。**

把計數器指向 Redis，讓限額回到它宣稱的意思：**每個已驗證客戶合計 60。**

刻意使用 Redis db 1——broker 佔用 db 0，而一次 `celery purge` 不該波及限流計數器。若 Redis 不可用，slowapi 降級為逐行程計數，而不是完全停用限流。

## 這推翻了什麼 ⭐

不是一個被寫下來的結論，而是更糟的東西：**一個沒有任何東西宣告它出錯的、未被言明的假設。**

> 限額靜默地比設定值高了 50%，而**沒有任何地方報錯。** 沒有 log、沒有告警、沒有測試失敗。**找到它的唯一方式是去數回應。**

這個教訓可以推廣到限流之外：

> **移除一份行程內狀態，不會讓行程變成無狀態的。它讓下一份狀態變得可見**——而那一份是靜默的。

把 API 變成多行程是一次分成兩半的變更，**而事前顯而易見的只有前半（掃描）。**
