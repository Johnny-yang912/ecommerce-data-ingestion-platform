# 2026-09-02 — Worker 水平擴展：倍率、代價，與 CAS 究竟有沒有上場

[English](../../en/verification/2026-09-02-worker-scale-out.md) | **繁體中文**

---

## 驗證的假設

同日的 [sync-handlers-before-after](./2026-09-02-sync-handlers-before-after.md) 結論八留下三個未經量測的主張，本文逐一驗證：

1. **「`try_claim_raw` 的 CAS 保證 worker 可以無協調地水平擴展」**——此前只有設計論證（[ADR-0004](../adr/0004-cas-claim-rowcount.md)），**從來沒有兩個 worker 同時消費同一個佇列的實測**。
2. 前一份文件的結論四說「天花板在 worker 不在 API」。那麼**加 worker 就能提高天花板嗎？倍率是多少？**
3. 結論八說突發期間 worker 由 270 降到 186 是「API 搶走 CPU」。那是**相關性推論**（注入一停就回升）。反向操作同一個變因會怎樣？

⚠️ 本文**沒有任何程式碼改動**。唯一的變因是 `celery worker --concurrency` 與容器數，兩者都是啟動參數。

## 環境

與 [sync-handlers-before-after](./2026-09-02-sync-handlers-before-after.md) 完全相同：

| 項目 | 設定 |
|---|---|
| 主機 | WSL2，16 核。壓測客戶端與服務同機 |
| 受測 API | `api-api:latest`（**改動後**的 image，`def create_order`），`docker run` 起在 8001 埠 |
| API 參數 | `UVICORN_WORKERS=4`、`POOL_SIZE=3`、`MAX_OVERFLOW=5`、OTel off、限流 off |
| Worker | `api-worker:latest`，`POOL_SIZE=2`、`MAX_OVERFLOW=2`（與 compose 一致），**容器數與 `--concurrency` 為本文變因** |
| 保留服務 | 僅 `db` / `redis`。api / worker / **beat** / otel-collector 與整組 Airflow overlay 全部停掉 |
| 負載 | 4 個客戶端行程、`order_id` 平移、各 15,000 筆，共 60,000 筆／輪。吞吐測試共 11 輪 = **660,000 筆** |

⚠️ **beat 必須停。** `scan_and_dispatch_task` 會把 pending 積壓分頁重派；積壓三萬多筆時單輪就會灌出上萬則重複訊息，把消化速率與 CAS 爭用一起量壞。

## 方法

### 測法一：突發負載（複刻測試 H）

與 [sync-handlers-before-after](./2026-09-02-sync-handlers-before-after.md) 測試 H 完全相同的腳本，**交替執行** W1（1 容器 × 4）→ W2（2 容器 × 4）→ W1 → W2，避免機器狀態漂移。每輪前 `redis-cli -n 0 flushdb`、之間 `DELETE FROM ods` → `DELETE FROM raw`（FK 順序）。

### ⭐ 測法二：純消化——為什麼非要有它不可

**測法一在雙 worker 下失效了，而失效本身就是一個發現。**

W2 的注入期間消化速率是 360.6 筆/秒，而注入速率是 361.4——兩者幾乎相等。也就是說 **worker 全程沒有被餵飽**，積壓在注入結束前就清空了。後果有二：

- 360.6 是**下界不是天花板**，不能拿來算倍率。
- 原本規劃的乾淨主指標（「注入結束後的消化速率」，因為那個窗口 API 與客戶端都閒置）**在 W2 下根本不存在**。

所以補一種測法：**worker 全停 → 灌 60,000 筆進佇列 → 停掉 API → 才起 worker，計時純消化。** 零 API 負載、零客戶端負載，量到的是 worker + Postgres 的真實上限。啟動時間另計（起容器到開始消化約 5 秒，兩種口徑都列）。

### ⭐ 測法三：CAS 爭用注入

**測法一與二從未讓 CAS 上場**——派工是點對點的，兩個 worker 本來就不會搶同一列。要驗證 CAS，必須刻意製造它：

worker 全停時建立 5,000 筆 pending → `flushdb` 丟掉 API 派出的原始訊息 → **對每個 `raw_id` 自行 publish 4 則重複訊息**（繞過 `main._enqueue` 與 `scan_and_dispatch`，因為那兩條路徑正是設計來避免這個情境的）→ 起 2 容器 × 8 子行程消化 → 從 worker log 清點 claim 事件。

**沒有這一格，後面所有對比都只是兩個不同日子的數字。**

### 測試 C — 純消化的擴展曲線 ⭐

零 API 負載、零客戶端負載，每組兩輪：

| 子行程 | 組態 | 純消化（扣除啟動） | 相對 4 | **每子行程** | pg 連線峰值 |
|---:|---|---:|---:|---:|---:|
| 4 | 1 容器 × 4 | 309.2 / 298.5（均 **303.9**） | 1.00× | 76.0 | 7 |
| 8 | 2 容器 × 4 | 512.8 / 517.2（均 **515.0**） | **1.69×** | 64.4 | 10 / 11 |
| 16 | 4 容器 × 4 | 789.4 / 789.4（均 **789.4**） | **2.60×** | **49.3** | 18 |

16 子行程兩輪完全相同（各 76 秒），沒有輪間漂移。

**三個獨立量測互相印證**：純消化 303.9、測試 A 的 W1 注入後消化 302、測試 H 原值 299——誤差 1.6% 以內。這同時證明測法一的「注入後」窗口確實是乾淨的。

### 測試 D — 連線佔用 ⚠️

| 子行程 | 編列預算 | **實測峰值** | 佔用率 |
|---:|---:|---:|---:|
| 4（1 容器） | 16 | **7** | 扣掉約 3 條基礎連線後 ≈ 4／16 |
| 8（2 容器） | 32 | **10–11** | ≈ 8／32 |
| 16（4 容器） | 64 | **18** | ≈ 16／64 |

**連線數 ≈ 子行程數 + 2~3，與編列的池大小無關。**

### 測試 E — 端到端正確性

11 輪 × 60,000 = **660,000 筆**，每一輪：

```
raw processed  = 60000        ODS 落地      = 60000
相異 order_id  = 60000        raw error 訊息 = （無）
```

`ods.raw_id` 與 `ods.order_id` **都有 UNIQUE 約束**，所以任何雙寫都會變成 IntegrityError、把該筆推進 `error` 終態。**零筆 error = 沒有任何雙寫抵達資料庫。**

⚠️ 但這**不等於 CAS 擋下了爭用**。`process.py:99` 的搶佔失敗只寫一行 WARNING 就返回，**不寫 ODS、不改 status、不進任何終態**——本測試的所有欄位對「CAS 是否曾經被觸發」都是盲的。零 error 同時相容於「CAS 擋下了爭用」與「爭用從未發生」兩種世界。要分辨，只能做測試 F。

### 測試 F — CAS 爭用注入 ⭐

5,000 筆 × 4 則重複訊息 = 20,000 則，2 容器 × 8 子行程：

| | 實測 | 預期 |
|---|---:|---:|
| **claim 失敗** | **15,000** | 15,000（= 5,000 × 3） |
| **處理完成** | **5,000** | 5,000 |
| claim DB 例外 | 0 | 0 |
| 「claim 成功但查無此筆資料」 | 0 | 0 |
| ODS 落地 / error | 5,000 / **0** | 5,000 / 0 |

兩個容器互有輸贏（失敗 7,663 / 7,337，成功 2,471 / 2,529）。同一筆的 4 則訊息全落在同一容器的機率約 1/8，故**約 87% 的記錄經歷了跨容器爭用**。

**機制**：兩個 worker 同時對 `WHERE id=? AND status='pending'` 下 UPDATE 時，後到者被行鎖擋住；前者 commit 後，Postgres 在 READ COMMITTED 下重新評估條件 → `rowcount = 0` → `try_claim_raw` 回傳 False。**這個結果與時序無關，所以計數是確定的 15,000，不是一個機率值。**

⚠️ **量測工具的陷阱：直接 grep 中文 log 會靜默 0 命中。** structlog 的 `JSONRenderer` 預設 `ensure_ascii=True`，`claim 失敗` 在 log 裡長這樣：`claim \u5931\u6557\uff0c...`。第一次清點因此拿到「claim 失敗 = 0」——那與「爭用沒發生」完全無法區分，而且不報錯。必須先 `json.loads` 再比對事件名。（同一個坑咬了兩次：修正用的 Python 腳本把 `\uXXXX` 寫進非 raw 的 docstring，直接 `SyntaxError`。）

## 結論

### 一、正常路徑上爭用不會發生——那不是 CAS 的功勞

多 worker 的端到端正確性成立：最多 16 子行程、4 容器，66 萬筆零重複、零遺失、無殘留。**這是此前沒有過的量測**——[ADR-0004](../adr/0004-cas-claim-rowcount.md) 與結論八第 3 點的水平擴展主張，在本文之前沒有任何一次量測跑過一個以上的 worker。

⭐ **但功勞在派工形狀，不在 CAS**：每筆 raw 對應一則指名 `raw_id` 的訊息，加上 Celery 的投遞語意（一則訊息只交給一個消費者）。測試 A–E 裡 **CAS 極可能一次都沒有被觸發**。

⚠️ 搶佔失敗在資料庫裡不留任何痕跡，所以「零 error」對「CAS 是否曾經上場」是盲的。**這兩件事必須分開陳述**——這正是測試 F 存在的理由。

### 二、爭用真的發生時，CAS 精確擋下——15,000 / 15,000 ⭐

測試 F 刻意製造 4 倍重複派工：claim 失敗恰為 15,000、處理完成恰為 5,000、ODS 恰為 5,000、零 error。**`rowcount == 1` 這個判準在跨容器併發下是確定性的，不是機率性的**——行鎖加 READ COMMITTED 的條件重評估保證了它。

這條路徑在真實系統裡由 `scan_and_dispatch` 的重派與 `POST /process_raw/{raw_id}?force=true` 觸發。本文以人工重複派工取代它們，因為那兩者的觸發時機不可控。

### 三、worker 可以水平擴展，但是次線性：4× 子行程只換到 2.60×

每次加倍的增益遞減：**1.69× → 1.53×**，每子行程產出由 76.0 掉到 49.3。

**但曲線沒有平掉。** 這一點決定了下一條結論。

### 四、瓶頸是 CPU，不是資料庫的併發能力

若天花板在 Postgres，8→16 這一步應該幾乎不動；實測仍有 1.53×。三個證據指向同一個方向：

1. **pg 連線數與子行程數精確線性**（7 / 10–11 / 18）——prefork 子行程一次只跑一個任務、同步持有連線，**完全沒有連線排隊或池爭用**。
2. **66 萬筆零錯誤**，沒有任何鎖等待或寫入衝突的跡象。
3. **每子行程產出單調下降**，正是 CPU 超額訂閱的特徵——16 個 worker 子行程加上 Postgres backend 與 Redis，在 16 核上無法各拿滿一顆核心。

⚠️ **精確地說，被排除的是 Postgres 的「併發上限」（鎖、連線、寫入爭用），不是 Postgres 的 CPU 消耗。** worker 與資料庫的 CPU 都在同一台機器上，本測法分不開兩者。

### 五、CPU 是零和的：worker 加倍，API 收單掉約 30%

| | 注入速率 |
|---|---:|
| worker 全停（6 個樣本） | ~534（全距 **441–577**，噪音大） |
| 4 子行程 | 499 |
| **8 子行程** | **366** |

結論八說「API 搶走 worker 的 CPU」；**反向同樣成立**——這回是對同一個變因做操作，不再是觀察相關性。

⚠️ **「4 子行程讓 API 掉 12%」這一步落在噪音裡，不成立。** 只有 8 子行程那一步（約 −30%）超出全距，而且它來自 W1/W2 交替執行的那組，受機器漂移影響最小。

### 六、端到端縮短 31%——唯一不需要歸因的指標

**239 秒 → 164 秒。** 積壓峰值、注入速率、消化速率三個數字各自被 CPU 重分配汙染（收得慢、出得快同時發生），但「60,000 筆全部落地 ODS 要多久」把三者一起吃進去了。

### 七、⚠️ worker 的連線預算超額約 4 倍——但不要照著砍

實測每子行程只用約 1 條（測試 D）。目前編列 `POOL_SIZE=2 + MAX_OVERFLOW=2`＝每子行程 4 條、每容器 16 條。

這與端點修正**前**的 API pool 是同一個形狀（見 [ingestion-capacity-and-bottlenecks](./2026-09-02-ingestion-capacity-and-bottlenecks.md) 測試 2）：連線持有窗口內沒有讓出點，所以一個執行單元同時只會持有一條。差別在於 **API 那邊的成因後來被修掉了，worker 這邊的成因是 prefork 模型本身，不會變。**

⚠️ 即便如此，**不要據此縮減預算**——那正是 [sync-handlers-before-after](./2026-09-02-sync-handlers-before-after.md) 結論五記錄的坑：上一個「實測只用 4 條，預算可砍到 8」的建議，在產生它的前提被移除後會直接造成 503。**餘裕是留給異常的**：資料庫降速時每個子行程的連線持有時間拉長，需求會上升。

### 八、容器邊界不影響擴展性

C8（1 容器 × concurrency 8）與 W2（2 容器 × 4）落在同一個噪音區間（注入 368.0 vs 361–370、消化 365.9 vs 360–369、積壓峰值 8,944 vs 6,420–9,383）。

**真正的變因是子行程總數，容器數本身不帶來任何東西。** prefork 子行程本來就是獨立行程、不共用 GIL——這正是「水平擴展」主張成立的機制，而它在單機上就能驗證。

**更新後可陳述的容量描述（必須連同環境一起引用）：**

> 於單機開發環境（16 核，DB / Redis / worker / 壓測客戶端同機，限流關閉）實測：Celery worker 在零 API 負載下的消化速率為 4 子行程 304 筆/秒、8 子行程 515 筆/秒、16 子行程 789 筆/秒——次線性但持續成長（每次加倍 1.69×、1.53×），瓶頸為單機 CPU 超額訂閱而非資料庫併發。突發期間 API 與 worker 互搶 CPU：8 子行程下 API 收單由約 534 筆/秒降至 366。60,000 筆突發全部落地 ODS 的端到端時間，由 4 子行程的 239 秒縮短至 8 子行程的 164 秒，積壓峰值由 36,321 降至 7,902，兩者皆零錯誤、零掉單。

## ⚠️ 本文不代表什麼

- **不代表生產環境數字。** 單機、16 核、壓測客戶端與服務同機、資料量約 1.7 萬筆基底。
- **沒有定位到 worker 的天花板。** 曲線在 16 子行程仍在上升，本文沒有量 32。
- **分不開 worker CPU 與 Postgres CPU。** 要分開得把 DB 移到另一台，或給容器上 `--cpus` 限制。
- **注入速率的機器噪音很大**（無 worker 時全距 441–577）。任何 10% 級別的注入速率差異在本文中都不可陳述。
- **`scan_and_dispatch` 與 `/process_raw?force=true` 這兩條真實的爭用來源仍未直接驗證。** 測試 F 是以人工重複派工模擬它們造成的**情境**，不是走它們的**程式路徑**。
- **沒有做故障注入。** 雙 worker 下「一個 worker 中途被 SIGKILL」的恢復行為未測——[2026-08-10-celery-sigkill-recovery](./2026-08-10-celery-sigkill-recovery.md) 只跑過單 worker。
- **限流全程關閉。** 線上是 `60/minute`。

## 這補上了什麼

⭐ **本文沒有推翻任何既有結論。** 它補的是三種缺口，每一種對應一種不同的「原本不夠硬」：

- **設計論證 → 實測**：主張寫在 ADR 裡，但從來沒有跑過一個以上的 worker。
- **相關性 → 操作同一變因**：原本是「注入一停就回升」的觀察，本文反向操作 worker 數，得到對稱的結果。
- **未限定的數字 → 補上前提**：原數字沒有錯，錯的是引用時沒有帶 worker 組態。

唯一稱得上「修正」的只有一處，而且修的是**理由不是結論**：水平擴展安全這件事成立，但功勞歸屬要換人。

| 同上，結論八的積壓數字<br>「峰值 36,526、注入後 119 秒消化完」 | 量測正確，但**沒有標註 worker 組態** | 那是 1 容器 × 4 子行程的值；8 子行程下是 **7,902 與 0 秒** | ✅ 原值不變。補的是引用條件：**積壓數字必須連同 worker 組態一起引用** |

| 同上，結論八第 3 點<br>「worker 若獨立部署或水平擴展，這個互搶就不存在」 | 推論 | 測試 C 在零 API 負載下量到 304／515／789 筆/秒，確認互搶是同機共用 CPU 的產物 | ✅ 成立 |
| [ingestion-capacity](./2026-09-02-ingestion-capacity-and-bottlenecks.md) 結論四<br>「天花板在 worker 不在 API」 | 觀察，**沒有量過那個天花板能不能買** | 倍率已知：4× 子行程 → 2.60×，次線性但曲線在 16 仍未平；瓶頸為單機 CPU 而非資料庫併發 | ✅ 成立，且**天花板是可以買的** |
| 同上，結論八推估表<br>「Worker 水平擴展｜可｜依據：CAS」 | 該表**自己標明全部未經驗證** | 三軸中第一個被實測的一軸 | ✅ 成立（次線性）。⭐ **依據欄要改**：主要機制是點對點派工，CAS 是爭用兜底 |

⚠️ **`raw_pending_watch` 的判讀基準隨 worker 組態而變。** 它量的是「最舊那筆躺多久」而非筆數，所以不會誤報；但積壓的**數量級**在 4 與 8 子行程之間差了 4.6 倍。
